# レポートの読み方と判定の仕様

生成されたレポートに出る各セクションの意味と、シート推奨を決めているロジックの前提。
分析結果を読む人・判定の妥当性を確かめる人向け。

- 環境構築: [setup.md](./setup.md)
- 入力データの準備と月次運用: [usage.md](./usage.md)
- 考察の自動執筆と公開テキストの検査: [tooling.md](./tooling.md)

成果物は役割で分かれている。report はサマリ・シート変更推奨・考察を読むための短い文書、
details は全ユーザ表・部署別/チーム別サマリ・詳細利用状況・組織内の分布・月中の推移・
シートが吸収した量の実測を集めた機械生成の詳細資料（感度分析は判定の版が v1 のときだけ）、
dashboard は同じ数値をタブに分けて見せる共有用の自己完結 HTML。

ファイル名は `{種別}-{YYYYMM}-{組織名}.{拡張子}`（例: `report-202607-<組織名>.md`）で、
共有でフォルダの外へ出してもどの組織のいつの分析かが分かる。以下では種別名だけで呼ぶ。

このほか、組織の担当者へ共有しない資料として、人 × 月の表（adoption-people）・チーム × 月の
表（adoption-teams）と、その2つの表から作るレポート（adoption-report）を `reports/summary/`
に書ける（既定は無効。[adoption-people の列](#adoption-people-の列人--月の表)・
[adoption-teams の列](#adoption-teams-の列チーム--月の表)・
[adoption-report](#adoption-reportレポート)）。

以下のセクション名は、断りがなければ details と dashboard の両方に出るものを指す。
片方にしか出ないものもあり、「シートが吸収した量の実測（E = API換算需要 − 実課金）」と
「感度分析」（v1 のときだけ）と、複数スペースの組織の「主と副の切り替え」は details だけ、
「Codeと他プロダクトの需要（API換算）」は dashboard だけに出る。
どちらの成果物でも、材料になるデータが無いセクションは省かれる。

設定について: 以下で `config.yaml > trend` のように書くのは設定のキーの位置を指す。既定値は
パッケージ同梱の `default-config.yaml` が持ち、ワークスペースの `config.yaml` には既定から
変えたい差分だけを書く（書かなかった項目は既定が使われる）。モデル単価やカラム対応表のように
プログラムの更新で新しい値が届く項目は、ワークスペース側に写さないこと。キーの一覧と上書きの
規則は[設定キーと既定値](#設定キーと既定値)。

## dashboard の構造と操作

共有用の自己完結 HTML。スタイル・スクリプト・データを1ファイルに埋め込んであり、外部への
通信を一切しないため、オフラインや外部アクセスを絞った環境でもブラウザで開くだけで読める。
内容は5つのタブに分かれる。
複数スペースの組織では組織タブの次に「複数スペース」タブが加わり、6つになる。

- 概要 — KPI 4枚（メンバー数・現在のシート費用・API換算利用額・削減見込み）と、月次推移・
  前月からの変化・追加クレジットの状態・月中のメンバー変動・主な増減
- 推奨アクション — 判定サマリ（判定ごとの件数）と追加クレジットの付与候補・設定確認を先に置き、
  その下に推奨一覧（ユーザごとの現在→推奨シート・API換算需要・実課金・削減/月・判定・理由）。
  v1 では付与候補だけで、推奨一覧には理由の代わりに Std時/Prem時が入る
- メンバー別 — ユーザ別 API 換算コスト（棒グラフ）、詳細利用状況、月中の利用推移、
  月中の Claude Code 活動、Codeと他プロダクトの需要（API換算）とその内訳表
- 組織 — 部署別サマリ・チーム別サマリ、組織内の分布（参考値）
- 前提と注意 — シート単価・V2 の判定基準・削減見込みの意味・方針線を ±$100 ずらした確度・
  判定に使用した月と必要な完全月数（既定は昇格 1・降格 2）。v1 では込み利用量の推定による
  Std時/Prem時・確度・上限フラグと、ヒステリシスの判定に使用した月を示す

タブ名の脇の数字はそのタブに載る件数（概要はメンバー数、推奨アクションは推奨一覧の行数、
メンバー別は詳細利用状況の行数、組織は部署別サマリ（部署が無ければチーム別）の行数）。
前提と注意は数えるものが無いので数字が付かない。どのタブでも、材料になるデータが無い
セクションは出ない。

右上の Light / Dark / Auto でテーマを切り替える。既定は Auto で OS の設定に追従し、明示的に
選んだテーマはそのブラウザに保存されて次に開いたときも保たれる。

対話でできることは次のとおり。

- 列ソート — 表のヘッダをクリックすると並べ替える（同じ列をもう一度クリックで逆順）。
  数値の列は降順、文字列の列は昇順から始まる
- 検索 — 人が並ぶ一覧には検索ボックスが付き、ユーザ名（メールアドレスのローカル部）と
  メールアドレスの部分一致で絞り込む（部署・チーム単位の集計表は対象外）
- 判定フィルタ — 推奨一覧のみ。判定（変更推奨・要観察 など）で絞り込む
- 高さの変更 — 表のスクロール領域は、その直下のバーをドラッグして縦の高さを変えられる
  （動かしても見え方が変わらない短い表にはバーが出ない）

一覧は表も棒グラフも最初から全行を表示する（絞り込みで隠れる行だけが減る）。

JavaScript が無効な環境でも内容はすべて読める。その場合は上記の操作用の UI が現れず、
すべてのタブの中身が見出し付きで縦に積まれる（テーマの切替ボタンも出ないが、明暗は OS の
設定に追従する）。

## 前月からの変化（正式分析のみ）

正式分析（`analyze`）では、過去月のスペンドがそろっていれば report / dashboard の
サマリ直後に「前月からの変化」セクションが出る。対象月と、その直前に存在する月
（欠月があれば飛ばした直前の月）を比べ、次を示す。

- 利用開始 / 利用停止 — 需要が新たに立ち上がった、または止まったメンバー
- 主な増減 — 需要が大きく増減したメンバーを増減額の大きい順に表示
- 実課金の新規発生 — 前月まで従量課金ゼロだったのに当月に発生したメンバー
- 月次推移 — 直近数ヶ月の API 換算需要・実課金・アクティブ人数

シートの判定には影響しない表示専用のセクション。初月（比較対象が無い月）は
出ない。表示閾値は `config.yaml > trend` で調整できる。

## 月中の利用推移（スナップショット差分）

同じ月のスペンドを、月初〜当日の累積で複数回エクスポートしておくと（例: 毎週金曜に
「7/1〜当日」でエクスポート）、それらの差分から月の途中での利用の伸び・停止を検出できる。
対象月の `spend/` に月初開始（1日〜）の累積エクスポートが2つ以上あると、正式分析・速報の
どちらでも「月中の利用推移（スナップショット差分）」セクションが自動で出る（フラグ不要）。
主データには従来どおり期間の広いファイルを使い、狭いファイルは差分の計算に使う。

- 停止疑い — 直近の区間で需要の伸びが止まったメンバー（休暇・案件の谷でも起こるため断定には本人確認が必要）
- 停止した Standard ユーザで実課金ゼロの場合、v1 では停止時点の累積需要を「シートに含まれる
  利用量（allowance）」の実測候補と説明する（従量課金が有効なら本来はそこで課金が始まるため）。
  v2 では停止時点の累積需要を示すが、実測候補という説明は付けない
- 込み量の消化 — 区間の途中で実課金が 0 から発生したメンバー（実効込み量がその区間の
  累積需要の間にあると分かる）

閾値（停止とみなす増分・停止判定の前提となる累積需要・判定する最小区間日数）は
`config.yaml > snapshot_diff` で調整できる。エクスポートは月初1日開始で揃えること
（1日開始でない期間のファイルは差分対象から外れる）。

### 月中のメンバー変動（members スナップショット）

members も同じ月に単日スナップショットを複数置くと（例: `members-...-2026-07-05.csv` と
`members-...-2026-07-16.csv`）、隣り合う時点の差分から月中のシート変更・メンバーの追加・
削除を検出し「月中のメンバー変動（スナップショット差分）」セクションに出す。日付付きの
members ファイルが対象月に2つ以上あると自動で発動する（月のみの `members_2026-07.csv` は
時点が定まらないため差分の対象外）。変動が無くてもセクションは出し、スナップショットを
取ったこと自体を記録する。v2 の警告は検出した事実を伝え、直近の加入・シート変更がある人は
「要観察」になる。v1 では当月の損益分岐判定を最新スナップショット時点のシートで行うため、
月中にシート変更があったユーザには参考値である旨の警告を添え、判定窓のあいだの加入・
シート種別の変更を変更推奨の保留条件にする（[判定ロジック概要](#判定ロジック概要)）。
コスト・削減見込みなどの数値そのものは変わらない。

### 月中の Claude Code 活動（code-analytics スナップショット）

code-analytics も同じ月に日付付きスナップショットを複数置くと、累積 LoC（あれば PR 数）の
月中の伸びを「月中の Claude Code 活動（code-analytics 差分）」セクションに出す。さらに
スペンドの停止疑いと email で突き合わせ、停止したユーザの LoC も止まっていれば「停止の傍証」、
逆に LoC が伸びていれば「利用継続の形跡あり（スペンドとの食い違いは要確認）」という注記を
停止疑いの箇条書きに添える。これも表示専用でシート判定には影響しない。

## Codeと他プロダクトの需要（API換算）（dashboard のみ）

メンバー別タブの下部に出る、金額（API 換算需要）を Code とそれ以外に分けて見るセクション。
棒グラフと内訳表の2つで構成される。対象は対象月のスペンドに明細のあるユーザで、利用ゼロの
メンバーと組織サービス利用の行は含まない。

- 棒グラフ — 需要の合計を棒の長さに、Code の割合を色の切り替え位置に取る。Code の需要を
  確定できないユーザは斜線の棒（内訳不明）になる
- 内訳表 — 需要（計）・Code需要・Code比率・他product需要・product数。他product需要 =
  需要（計） − Code需要。「—」は確定できなかった値で、0 ではない
- ⚑ — 補助プロダクト（`product_policy.supplementary` に挙げた product）の需要が
  `supplementary_high_usd` 以上であることの印。他product需要のセルに付くが、判定に使うのは
  supplementary に挙げた product の需要合計なので、どちらの分類にも書いていない product の
  需要は額には含まれても ⚑ には効かない

活用の見え方を示す表示専用のセクションで、シートの判定・推奨には使わない
（判定は全 product の需要で行う）。

「詳細利用状況」の product構成 とは基準が違う。あちらは利用回数（リクエスト数）基準の構成比で、
こちらは金額（API 換算需要）基準。回数の多い product と金額の大きい product は一致しないため、
2つの並びが違っていてもデータの矛盾ではない。

### product の分類（config.yaml > product_policy）

上のセクションと usage-summary の `supplementary_high` / `prohibited_observed` 列は、
この設定を根拠に計算される。シート判定に使う需要は分類に関係なく全 product の合計で、
この設定が変えるのは活用の見方だけ。

- `primary` — 活用評価の主軸にする product。ここに挙げたものの需要が「Code需要」になる
  （既定は Claude Code）。空にはできない
- `supplementary` — 補助的な利用面（既定は Chat・Cowork・Claude Design・Research・
  Code Review・Claude Tag・Claude in Chrome・Office Agents・Other と、置き換えられた以前の名前の
  Claude in Slack・Claude in Slack (legacy)）
- `prohibited` — 組織の方針で使わせない product（既定は空）。観測されると警告に出る。
  シート判定には影響しない
- `supplementary_high_usd` — supplementary の需要合計がこの額以上なら ⚑（既定 $100/月）

primary と supplementary は排他で、同じ product 名を両方に書くとエラーになる。prohibited は
分類と直交する指定なので、primary・supplementary に挙げた product を重ねて書いてよい。

product 名は、支出レポートの `product` 列に現れる表記で書く。照合は、正規化（前後空白の除去・
大小文字・Unicode の正規化形式）後の完全一致で行う。部分一致・あいまい一致はしない
（`Code Review` が `Claude Code` に一致するような取り違えは、費用ではなく活用の評価を歪めるため）。
CSV 側の表記ゆれは、リストに名前を並べて吸収する。

primary にも supplementary にも無い名前の product が対象月の利用者の明細にあると、
正式分析の実行時に workspace ごとに 1 件警告し、CSV に現れた表記と該当する利用者の人数を示す。
警告は成果物に載らず、終了コードも変わらない。速報と doctor では出ない。名前が空の行と
組織サービス利用の行は対象外。設定で分類するときは、この節の「一覧を変えるときは」の段落を参照。

既定の `supplementary` には、支出レポートに現れる primary 以外の名前を並べる。置き換えられた
以前の名前も残し、以前の名前で書き出された CSV を分析するときに同じ利用面として数える。
`Other` は特定の product に帰属しない利用を表す値。

一覧を変えるときは、ワークスペースの `config.yaml` に一覧の全体を書く。リストは丸ごと置き換わる。

`supplementary` を上書きしていない設定で、既定の `supplementary` に足した名前を `primary` に
書いていると、既定の一覧と名前が重複し、設定の読み込み時にエラーになる。その名前を外した
`supplementary` の全体も書けば、これまでの分類を保てる。`supplementary` を上書きしている
設定には、既定に足した名前は入らず、このエラーにもならない。

## recommendations の列

判定（シート推奨）をユーザ単位で並べた表で、スプレッドシートでの二次加工に使う。行は
members ∪ 対象月のスペンドのユーザで、利用ゼロのメンバーとシート未割当のメンバーも含み、
組織サービス利用の行は含まない。並びは判定（`status`）ごとにまとめ、同じ判定の中は削減見込みの
大きい順（複数 workspace の組織では workspace ごと）。

既定（v2）は V2 判定の結論を並べる。列は次の順になる。

- `email` — ユーザのメールアドレス
- `workspace` — 複数スペースの組織でだけ `email` の次に出る列で、そのアカウントの workspace
  （ディレクトリ名）。行は主→副の順に全スペースのアカウントを並べ、主の行の `api_cost_usd` は
  判定に使った全スペースの合算（[複数スペース（workspace）の組織の成果物](#複数スペースworkspaceの組織の成果物)）。
  片方のスペースにしか無い列は、もう片方の行で空欄になる
- `current_seat` — 現在のシート（`standard` / `premium` / `unassigned` / `unknown`）。`unknown` は
  members に居ないのにスペンドに現れたユーザ
- `api_cost_usd` — 対象月の全 product の API 換算需要 [USD/月]
- `cost_current_usd` — 現シートの月額（シート料 + 実課金）。シート未割当と `unknown` の行は空欄
- `recommended_seat` — 昇格なら `premium`・降格なら `standard`、それ以外は現シート
  （シート未割当の行は `unassigned`）
- `monthly_saving_usd` — シート差額ベースの比較額。降格はシート差額、昇格は実課金 − シート差額、
  現状維持は 0、判定しない行は空欄。変更後の従量課金を含まず、負は費用増を表す
- `status` — V2 の結論。`変更推奨` は昇格・降格、対象月が部分月か完全月の履歴が足りない行は
  `要観察（データ蓄積待ち）`、直近の加入・シート変更や照合の食い違いがある行は `要観察`。
  ほかに `現状維持`・`シート不明`・`対象外（シート未割当）`・`対象外（固定シート）`・
  `対象外（副スペース）` がある
- `confidence` — 方針線を ±$100 ずらしても、シートを変えるかどうかの結論が同じかを表す。
  どちらにずらしても同じなら `高`、片方で変われば `中`、両方で変われば `低`。
  追加クレジットの提案は比べず、判定を保留した行・判定しない行は `—`
- `reason` — 判定の理由。複数あるときは「; 」区切り
- `billed_extra_usd` — 対象月の実課金（スペンドレポートの `net_spend` の合計。列の無いレポート
  では 0）
- `prompt_tokens` / `completion_tokens` — 対象月の prompt / completion トークン数の合計
- `product_breakdown` — product の構成比（リクエスト数基準。リクエスト数の列が無ければ明細の
  行数で数える。1% 未満は省く）。スペンドレポートに product の列が無ければ空欄
- `model_breakdown` — モデルの利用割合（prompt + completion のトークン量基準。1% 未満は省く）
- `department` / `team` / `role` / `note` — members-info.csv の部署・チーム・職種・備考（兼務は
  `; ` 区切り）。列は常に出て、members-info が無い組織や行の無いユーザでは空欄
- `credit_limit_usd` / `credits_mode` — 追加クレジット上限 κ（空欄は不明・`inf` は上限なし）と、
  そこから導いたモード（`enabled` / `disabled` / `unknown`。上限が空欄でも対象月までに実課金が
  観測されたユーザは `enabled`）。上限が決まっているユーザが1人以上いる（members-info の列に
  値があるか、workspace の設定に `credit_limit_default_usd` がある）ときだけ出る列で、そうで
  なければ2列とも落ちる（[追加クレジット（usage credits）の上限](#追加クレジットusage-creditsの上限)）
- `prs_with_cc` / `loc_with_cc` — code-analytics の PR 数と LoC。対象月の code-analytics があり、
  その列を持つときだけ出る。code-analytics に行の無いユーザも 0 になる

判定の版が v1 のときは `reason` が無く、次の5列が加わる。
`api_cost_usd` の次に `cost_if_standard_usd` / `cost_if_premium_usd`（そのシートだった場合の
月額。mid シナリオ）が入り、現シート側はシート料 + 実課金の観測値、変更先側はモデルの試算を
観測実課金で抑えた値になる。シート未割当と固定シートの行は空欄。
`confidence` の次に `rec_low` / `rec_high`（low / high シナリオの推奨シート）、
`cap_suspected`（上限フラグ。True / False）が入る
（[V1 の判定](#v1-の判定--decision-version-v1)）。次の列の意味も v1 では異なる。

- `recommended_seat` — mid シナリオで月額の安い方のシート（同額なら `standard`）。シート未割当の
  行は `unassigned`、固定シートの行は現シートのまま
- `monthly_saving_usd` — `cost_current_usd` から安い方の月額を引いた削減見込み（現シートが
  推奨どおりなら 0）。シート未割当・固定シート・`unknown` の行は空欄
- `status` — `変更推奨` はヒステリシスの条件を満たしたときだけ。推奨が現シートと違っても、
  判定窓（対象月から暦で遡る `decision.hysteresis_months` か月）の月がそろっていない
  （欠月・部分月・副スペースの欠け）とき、判定窓のあいだに加入・シート種別の変更があったときは
  `要観察（データ蓄積待ち）`。ほかに `要観察`・`現状維持`・`シート不明`・
  `対象外（シート未割当）`・`対象外（固定シート）` がある
- `confidence` — low / high シナリオの推奨のうち mid と一致した数（2 = `高`・1 = `中`・
  0 = `低`）。シート未割当と固定シートの行は `—`

v2 の主 workspace の `recommended_seat`・`monthly_saving_usd`・`status`・`confidence`・`reason` は、
decision-evidence の同じ email の行（複数 workspace の組織では email と workspace の列で対応づける）
から作る。副 workspace の行は decision-evidence に無く、副の規則（`対象外（固定シート）`・
`対象外（副スペース）`・`シート不明`・`対象外（シート未割当）`）で決まる。

金額は小数2桁に丸める。値の無いセルは空欄で、真偽値は True / False で書く。文字コードは
BOM 付きの UTF-8 で、先頭が `=`・`+`・`-`・`@`・タブ・CR の文字列のセルには、表計算ソフトが
式として解釈しないよう先頭に `'` を付ける。

## usage-summary の列

ユーザ単位の product 利用特徴量。email + 8つの特徴量の計9列（複数スペースの組織では email の
次に `workspace` 列が入り計10列。[複数スペース（workspace）の組織の成果物](#複数スペースworkspaceの組織の成果物)）
で、行は対象月のスペンドに明細のあるユーザ（メールアドレス昇順）。利用ゼロのメンバーは行を
持たないため recommendations とは対象がそろわず、組織サービス利用の行も含まない。

- `email` — ユーザのメールアドレス
- `total_demand_usd` — 全 product の API 換算需要 [USD/月]
- `code_demand_usd` — primary に挙げた product の需要
- `code_demand_share` — `code_demand_usd` ÷ `total_demand_usd`（需要の合計が 0 のユーザは
  比を定義できないため空欄）
- `total_requests` — 全 product のリクエスト数
- `code_requests` — primary に挙げた product のリクエスト数
- `product_breadth` — そのユーザの全リクエストの 5% 以上を占める product の数
- `supplementary_high` — supplementary の需要合計が `supplementary_high_usd` 以上か（True / False）
- `prohibited_observed` — prohibited に指定した product の明細行が1行でもあるか（True / False）

金額は小数2桁、比率は小数4桁で書き出す。値は分析時に計算したものをそのまま出しており、この
CSV のための再計算はしない。

確定できなかった値は空欄にする。0 や False で埋めると「観測した結果が 0 だった」ことと区別が
つかなくなるため、欠損は欠損のまま出す。product 名が空の明細行があるユーザや、product 列
そのものが無いスペンドレポートでは、その行をどう数えるかで結論が変わる特徴量が空欄になる
（変わらないものは確定した値が入る）。

## decision-evidence の列（V2 判定）

V2 判定の結論と、その結論を出すのに使った材料。判定の版が v2 の実行では、report / details /
dashboard / recommendations の判定もこの結論から作る。recommendations の主 workspace の行の
`status`・`recommended_seat`・`monthly_saving_usd`・`confidence`・`reason` が、この CSV の
同じ email の行（複数 workspace の組織では email と workspace の列で対応づける）に対応する。
副 workspace の行はこの CSV に無い。

出力するのは正式分析で判定の版が v2 のときだけ。版は「CLI の `--decision-version` の明示指定 >
`config.yaml > decision.version` > 既定の v2」で決まる。`--decision-version v1` を渡せばその実行は
V1 判定になり、この CSV を書かない（前回の実行で書いたものが残っていれば、実行時の出力で
知らせる）。速報モード（`--preview`）は V2 判定を行わないため出力されず、`--decision-version`
との併用もできない。

行は主 workspace の members ∪ 対象月のスペンドのユーザ（メールアドレス昇順）で、
recommendations の主 workspace と同じ対象。

- `email` — ユーザのメールアドレス
- `workspace` — 複数 workspace の組織（config の `workspaces` が2つ以上）でだけ `email` の
  次に出る列で、主 workspace の名前。複数アカウントを持つ人は主 workspace の行1本にまとめ、
  需要（全 product）は全 workspace の合算、実課金・κ・現シート・シート変更は
  主 workspace の値を使う。副 workspace にだけアカウントがある人の行は無い
- `subject_id` — 解決した stable ID（`account:` / `user:` / `email:` の接頭辞つき。確定できなければ空欄）
- `identity_quality` — `stable` / `email_consistent` / `email_fallback` / `conflict` / `unresolved`
  （複数 workspace の組織では、副 workspace でその email の Identity が衝突した場合も
  `conflict` になるが、`subject_id` は主 workspace の解決結果のまま）
- `current_seat` — 対象月末時点のシート（`standard` / `premium` / `unassigned` / `unknown`）
- `month` — 対象月
- `complete` — 対象月のスペンドが全月ぶんか（True / False）
- `complete_months` — 履歴のうち完全月（`;` 区切り・昇順）
- `total_demand_usd` — 対象月の全 product の API 換算需要 [USD/月]
- `billed_extra_usd` — 対象月の実課金
- `credit_limit_usd` — 追加クレジット上限 κ（空欄は不明・`0.00` は無効・`inf` は上限なし）
- `premium_justification_usd` — 判定に使った方針線（`decision_v2.premium_justification_usd`）
- `status` — 結論（`recommended` / `observe` / `no_decision` / `keep` / `excluded`）。
  `excluded` はシート未割当のほか、主 workspace に `fixed_seat` を設定した組織の
  Standard / Premium のアカウントにも付く
- `seat_action` — シートへの推奨（`upgrade_to_premium` / `downgrade_to_standard` /
  `keep` / `none`）
- `credit_action` — 追加クレジットへの推奨（`enable_with_cap` / `review` / `keep` / `none`）
- `reason_codes` — 判定の根拠・保留理由（`;` 区切り・主理由 → 補助 → 情報の固定順）
- `policy_stability` — 方針線を ±$100 ずらしても同じ seat action になった数（1〜3。経済軸に
  到達しない判定は空欄）
- `suggested_credit_cap_usd` — `credit_action` が `enable_with_cap` のときに提示する初期上限

金額は小数2桁、確定できなかった値は空欄にする（usage-summary と同じ流儀）。語彙の一覧と
各理由コードの意味は[実装設計書の §12](./roadmap/implementation-design.md#12-decision-v2) が唯一の源。

履歴（判定が見る月の並び）は次のように組む。

- 対象月から古い方へ遡り、暦で連続する月だけを採る（間に欠月があればそこで打ち切る）
- 複数 workspace の組織では、副 workspace にシートのあるアカウント（Standard / Premium と、
  スペンドにだけ現れる不明）がある人について、副の部分月を不完全月に数え、副を使い始めた後に
  副のスペンドが無い月（欠月）があればその月以前を履歴から外す。副にシートの無い人（副で
  未割当の人を含む）の履歴は主 workspace のまま
- スペンドに明細が無い月は需要ゼロの観測として入れる（利用ゼロは観測であって欠損ではない）
- シート変更 event から加入が読み取れる場合は、加入より前の月を履歴から外し、加入がまたがる
  月を完全月に数えない（在籍が月全体に及んでいない月を完全月として扱わないため）

既知の制約が3点ある。

- 日付つきの members スナップショットが2つ未満の組織では加入・シート変更の event を作れない。
  この場合は加入の考慮が働かず、実際には在籍していなかった月も需要ゼロの観測として履歴に入る
- Identity は対象月の行だけで解く。月をまたいだメールアドレスの変更は同一人物として束ねない
  （過去の全期間を一括で解くと、退職者のアドレスが再割当された場合に別人どうしが1人へ結合する）
- 管理画面の当月消費（`input/<組織名>/admin/`）はまだ読まない。実課金はスペンドレポートの
  `net_spend` 由来で、この列を持たない旧形式のレポートでは実課金 0 として扱う

## github-summary の列（GitHub の参考値）

GitHub の merged PR 数・リードタイム・コミット単位の行数の参考値。GitHub 分析を有効に
した組織で、対象月のキャッシュ（`collect --source github`）があるときだけ正式分析が書く。

シートの判定には一切使わない。report / details / dashboard / recommendations /
usage-summary の内容はこのファイルの有無で変わらず、逆にこのファイルの値が判定へ入る
こともない。PR 数・リードタイム・行数はチームの働き方と repository の性質に強く依存するため、
値の大小から因果（活用度が高い・低い）を断定する材料にはならない。個人行はメール
アドレス昇順で、件数の多い順には並べない（個人のランキングを作らないため）。

行は次の2種類で、`scope` 列が区別する。

- `user` — 対象者のうち、`members-info.csv` の `GitHub ID` 列に login を書いた人。その月の
  PR が 0 件の人も行を持つ（0 件であることも参考情報のため）
- `organization` — 末尾の1行。組織全体の値で、集計から外した分の内訳もここに入る

対象者は、その月にこの組織でシートを持つ人で、分析が採用したメンバー一覧で Standard か
Premium と確認できた人を指す。複数スペースの組織では、分析したスペースのどれかで持てば
対象になる（まだ始まっていないため分析から飛ばしたスペースは見ない）。シート未割当の人と、
シート種別を確認できない人（メンバー一覧に居ない人を含む）は対象外。月内の在籍期間は
復元しないので、採用したメンバー一覧に載っていれば途中加入でも月全体が対象になり、
載っていなければ途中退任でも月全体が対象外になる。

この対象者の定義は 1.4.1 からで、1.4.0 までは個人行がシートの有無を問わず、
組織全体行は対応表に無い作成者と削除済みアカウントの PR も件数とリードタイムに含んでいた。
前の版の CSV と比べるときは、同じ版で作り直してから比べる。

各列の意味は次のとおり。

- `scope` — 行の単位（`user` / `organization`）
- `email` — ユーザのメールアドレス（組織全体行は空欄）
- `github_login` — 対応表に書かれた GitHub の login（組織全体行は空欄）
- `month` — 対象月
- `merged_pr_count` — その月に merge された PR の件数。個人行は本人が作成した分、
  組織全体行は対象者の PR（個人行の合計）
- `lead_time_median_hours` / `lead_time_p75_hours` / `lead_time_p90_hours` —
  `merged_at − created_at` の時間（小数1桁）。Draft だった期間も含み、日時は UTC で
  計算する。3点はいずれも線形補間の百分位（Excel の `PERCENTILE.INC` と同じ）で、
  母数はその行の `merged_pr_count` の PR。PR が 0 件の行は3列とも空欄
- `unmapped_authors` — 対象者の login に当たらない作成者の人数（組織全体行のみ）。
  対応表に無い人と、対応表にあっても対象者でない人の両方を含む
- `unmapped_prs` — その作成者による PR の件数（組織全体行のみ）
- `bot_prs` — Bot が作成した PR の件数（組織全体行のみ）
- `deleted_author_prs` — 作成者が削除済みアカウントの PR の件数（組織全体行のみ）
- `excluded_repository_prs` — 対象外 repository の PR の件数（組織全体行のみ）
- `total_prs` — キャッシュが持つ PR の全件数（組織全体行のみ）。組織全体行の
  `merged_pr_count` に `unmapped_prs`・`bot_prs`・`deleted_author_prs`・
  `excluded_repository_prs` を足した数に一致する
- `cache_complete` — 対象月の収集を読み切ったか（True / False）。False のときの件数は
  部分的な値
- `commit_count` — 作者に帰属したコミットの件数（大きな変更を含む）
- `lines_added` — そのコミットの追加行の合計（大きな変更を含む）
- `lines_removed` — そのコミットの削除行の合計（大きな変更を含む）
- `lines_added_capped` — 大きな変更を除いた追加行の合計
- `large_commits` — 大きな変更の件数
- `unresolved_author_commits` — 対象者に帰属できなかったコミットの件数（組織全体行のみ。
  個人行は空欄）。ほかのコミット5列の組織全体行は個人行の合計

repository 名・GitHub の Organization 名・対象者に当たらない作成者の login はこのファイルに
書かない（対象外 repository と対象者に当たらない作成者は件数だけを載せる）。

次の場合は書かず、実行時の出力に理由と次の一手を出す。

- 対象月のキャッシュが無い（`collect --source github` をその月について実行していない）
- キャッシュに repository の一覧が無い（一覧を保存する前に作られたキャッシュ。収集を
  もう一度実行すると一覧が付く）
- 速報モード（`--preview`）

対象月のキャッシュがコミットを持たない場合（schema 1 のキャッシュ）は、行数に関する
末尾の6列だけを空欄にする。実行時に `GH_COMMITS_MISSING: ` を先頭に付けた通知で、`collect` の
再実行を案内する。
PR の件数・リードタイムなど既存の列は引き続き書く。

前回の github-summary が残っている場合もツールは消さない。有効にした組織で書けなかった
実行では、そのファイルが今回は更新されないことを伝える。`organizations` から外した組織に
ついては、残っているファイルにも触れない。

### コミット単位の行数

対象月の repository の一覧にある PR のコミットを材料とする。Bot・draft・削除済みの
作成者の PR も対象に入れる。マージコミット（親が2つ以上）と、PR のマージで新しく
作られたコミットは数えない。後者は `merge_commit_oid` がその PR 自身の `commits` に
無いものを指し、この識別だけは対象外 repository を含む、読んだキャッシュの全 PR を見る。

同じ oid が複数の PR に出るときは、最も早く merge された PR に1回だけ帰属させる。
同時刻なら repository 名の小文字・PR 番号の昇順で決める。月をまたぐ重複を除くため、
対象月の前の `github.commit_lookback_months` か月のキャッシュも読み、そこの対象 PR に
出た oid は数えない。前の月にも対象月の repository の一覧を使い、過去の一覧は使わない。
前の月のキャッシュが無い・コミットを持たない・収集が完了していない場合は、月と理由を
実行時に通知する。未完了でも保存済みのコミットは重複除外に使う。設定が0なら前の月を
読まないため、この通知も出さない。

作者の login が対象者の対応表に当たればその人の行数にする。当たらず login が無いときと、
作者が Claude のとき（作者の login が `claude`。大文字小文字を区別しない）は、帰属する
PR の作成者が対象者ならその人へ帰属させるため、別の人のコミットが混ざる可能性がある。
そのほかの login で対象者に当たらない場合は PR の作成者へ戻さない。解決できない作者は
`unresolved_author_commits` の件数だけ残し、行数には入れない（実行時にも件数を警告する）。
コミットの作者のメールアドレス（`author_email`）は使わない。

人が作者で Claude が共著者（`Co-authored-by` の行）のコミットは、作者の人に帰属する。
共著者の側にだけ対象者がいるコミットは、その人の行数に入らない。

追加行が `github.large_commit_lines` を超えるコミットは「大きな変更」として
`lines_added_capped` から外す。閾値と同じ値は外さない。大きな変更も `commit_count`・
`lines_added`・`lines_removed` には含め、`large_commits` に件数を残す。ファイル単位では
除外しない。

コミットが250件を超える PR は保存された分だけを同じ規則で数え、超えた分を数えられない
ことを PR の本数とともに警告する。rebase マージ・cherry-pick などで SHA が変わった
コミットは別のものとして数える。行数の合計は PR の正味の差分とは一致しない
（同じ行を書き直したコミットもそれぞれ数える）。

## adoption-people の列（人 × 月の表）

Claude Code の活用（需要・リクエスト数・Claude Code が加えた行）、GitHub の成果（PR と
コミット単位の行数）、OpenTelemetry から数えた使い方を、1人の1か月を1行にして並べた CSV。
月ごとの変化を読むための材料で、人ごとの値は参考値として扱う。

既定では書かない。`config.yaml` に次を書くと、正式分析のたびに、分析した組織ごとに
`reports/summary/adoption-people-<YYYYMM>-<組織名>.csv` を書く（1組織だけの実行でも書く）。
同じ設定・同じ実行で、チーム × 月の表（adoption-teams）とレポート（adoption-report）も書く。
速報モード（`--preview`）ではどれも書かず、そのことを実行時に1行知らせる。GitHub 分析を
有効にしていない組織や OpenTelemetry を設定していない組織でも書ける。未設定の入力の状態は
`github_data`・`otel_data` に `not_configured` と書き、その入力に由来する値の列は空欄にする。

```yaml
adoption:
  enabled: true
```

読者は CTO と開発責任者を想定している。組織の担当者へ共有する成果物（report・details・
dashboard・recommendations・usage-summary・preview・preview-dashboard と、判定の版が v2 の
ときの decision-evidence、GitHub 分析を有効にした組織の github-summary）には含めないので、
`reports/<組織名>/` ではなく `reports/summary/` に置く。考察の執筆（`discuss`）の資料にも
ならない。

シートの判定には使わない参考値で、ほかの成果物の内容はこの設定の有無で変わらない。人ごとの
値を個人の順位づけに使わないこと。行はメールアドレスの昇順・月の昇順に並べ、量の多い順には
並べない。github-summary と同じく、値の大小から因果（活用度が高い・低い）を断定する材料にも
ならない。

行と月は次のとおり。

- 行は、その月にこの組織でシートを持つ人 × 月。シートを持つ人の定義は github-summary の
  対象者と同じ（その月の分析が採用したメンバー一覧で Standard か Premium と確認できた人。
  複数スペースの組織では分析したスペースのどれかで持つ人）
- 複数スペースの組織では人（メールアドレス）ごとに1行にまとめ、需要・リクエスト数・
  Claude Code が加えた行はアカウントの値の和にする
- 月は、入力に spend がある月のうち対象月以前のすべて（対象月を含む）
- 各月の値は、その月を対象月として分析したときの値にする。対象月の行は、同じ実行の
  usage-summary・github-summary の同じ人の値と一致する。過去の月も実行のたびに分析し直して
  作り直し、前回のファイルに追記しない（入力を直せば過去の月の行も変わる）。所属とシートの
  種別も、その月の分析が採用した members-info とメンバー一覧による
- 過去の月が入力の欠け（始まっているスペースの spend が無い月など）で分析できないときは、
  その月の行を書かず、実行時に月と理由を通知する。残りの月の行と対象月の成果物は書く

各列の意味は次のとおり。

- `email` — メールアドレス
- `month` — 月（YYYY-MM）
- `seat` — その月のシート種別（`standard` / `premium`）。複数スペースでシートを持つ人は、
  主のスペースを先頭に `+` でつなぐ（例 `standard+premium`）
- `department` / `team` / `role` — その月の分析が採用した members-info の部署・チーム・職種
  （未記入は空欄）
- `spend_complete` — その月の spend が全月データか（True / False）。複数スペースの組織では、
  分析した全スペースが全月のときだけ True
- `total_demand_usd` — 全 product の需要（API 換算・USD）
- `code_demand_usd` / `code_requests` — Claude Code の需要とリクエスト数
- `loc_with_cc` — Claude Code が加えた行（code-analytics）
- `github_id` — GitHub ID の対応表（members-info の `GitHub ID` 列）でのその人の状態。
  `login`（login を記入）・`none`（`なし` と記入＝対象の Organization で開発しない人）・
  `unset`（未記入か、行が無い）。GitHub 分析を有効にしていない組織は空欄
- `github_data` — その月の GitHub の材料の状態（下の表）。月ごとに全員同じ値
- `github_cache_complete` — その月のキャッシュの収集が完了したか（True / False）。False の
  月の値は部分的。キャッシュが無い月と GitHub 分析を有効にしていない組織は空欄
- `merged_pr_count` / `lead_time_median_hours` — その人が作成し、その月に merge された PR の
  件数と、lead time の中央値（小数1桁。PR が 0 件の人は空欄）
- `commit_count` / `lines_added_capped` / `large_commits` — その人に帰属したコミットの件数・
  大きな変更を除いた追加行・大きな変更の件数（[コミット単位の行数](#コミット単位の行数)）
- `cost_per_merged_line_usd` — `code_demand_usd` ÷ `lines_added_capped`（小数4桁）。分母が 0
  か、どちらかが空欄なら空欄
- `outside_org` — この Organization に成果が見えない月か（True / False）。GitHub ID が
  `login`・`github_data` が `ok`・`github_cache_complete` が True・`loc_with_cc` が空欄でない
  行だけが値を持ち、それ以外は空欄。加えた行が設定の下限以上で、コミットもマージ PR も
  0件なら True、それ以外は False
- `outside_org_months` — その月を含め、暦で連続して該当した月数（整数）。True なら1以上、
  False なら0、空欄なら空欄。非該当・判定できない月・その人の行が無い月（シートなし・
  分析できずに飛ばした月）で途切れ、次の該当月から1に戻る。表の最初の該当月も1
- `otel_data` — その月の OpenTelemetry の材料の状態（下の表）。月ごとに全員同じ値
- `otel_coverage` — その人の網羅率の状態（`ok`・`not_judged`・`low`・`missing`・`unknown`）。
  判定の規則は [届いている割合の検査（doctor）](#届いている割合の検査doctor) を参照
- `otel_active_days` — OpenTelemetry のリクエストがあった UTC 日の日数
- `otel_prompts` / `otel_custom_command_prompts` — 指示の回数と、そのうち自作のコマンドを使った
  回数（プラグインのコマンドを含む）
- `otel_requests` — OpenTelemetry のリクエスト数（`api_request` のうち `origin` が `main`・
  `sdk`・`subagent_builtin`・`subagent_custom` のもの。要約や題名の生成などの補助の呼び出しを除く）
- `otel_subagent_requests` / `otel_custom_subagent_requests` — サブエージェント経由のリクエスト数と、
  そのうち自作のサブエージェント経由のリクエスト数
- `otel_skill_requests` — スキルを使ったリクエスト数（組み込みと自作を含む）
- `otel_interactive_decisions` / `otel_interactive_decisions_asked` — 端末の対話で編集・コマンド・
  MCP の実行を許可・却下した判断の件数と、そのうち確認の画面で人が答えた件数
- `otel_mcp_decisions` — MCP の実行を許可・却下した判断の件数（端末の種類を問わない）

需要とリクエスト数は usage-summary の同名の列と、GitHub の列は github-summary の同名の列と
同じ値・同じ書式で書く。`loc_with_cc` は report・details の LoC と同じ値。その月の spend に
行の無い人の需要とリクエスト数は 0、code-analytics に行の無い人の `loc_with_cc` は 0 にする。
確定できない値（product の列が無い spend での Claude Code の需要など）と、LoC の列を持つ
code-analytics がどのスペースにも無い月の `loc_with_cc` は空欄にする。

GitHub の列（`merged_pr_count` から `large_commits` まで）は、`github_id` が `login` の人だけが
値を持つ。`github_data` は上から順に最初に当てはまるものにする。

| 値 | 意味 | GitHub の列 |
|---|---|---|
| `not_configured` | GitHub 分析を有効にしていない組織 | すべて空欄 |
| `no_cache` | その月のキャッシュが無い | すべて空欄 |
| `no_repository_list` | キャッシュに repository の一覧が無い | すべて空欄 |
| `no_commits` | キャッシュがコミットを持たない（以前の版で作った形式 1 のキャッシュなど） | PR の列だけ書く |
| `no_previous_month` | 直前の月のキャッシュが無いか、コミットを持たない | PR の列だけ書く |
| `ok` | 上のどれでもない | 書く |

直前の月（暦で1つ前）のキャッシュが無いかコミットを持たない月は、月をまたいで同じ
コミットを除けず行数が多く出るため、コミットの列を空欄にする（時系列に並べたとき、その月
だけ多く見えないようにする）。github-summary は1か月の値なので、同じ月でもコミットの列に
値を書き、前の月が揃っていないことを通知する。`github.commit_lookback_months` が 0 のときは
前の月を読まない設定なので、この扱いをしない。直前の月の収集が完了していないだけなら
読めた扱いにし、直前の月が読めれば、それより前の月が欠けていてもコミットの列を書く。
最初の月から行数を出したい場合は、その前の月のキャッシュも収集しておく。

収集が完了していない月も、状態は上の表で決める。値が部分的であることは
`github_cache_complete` で読む。

管轄外の検知（`outside_org`）の行数の下限は `adoption.outside_org_min_lines`（既定 1000）で、
Claude Code が加えた行の下限を1以上の整数で指定する。下限ちょうどは該当し、1行でも少ない月や
コミット・マージ PR のどちらかが1件でもある月は該当しない。`なし`・未記入の人と、判定に
要る材料が確定できない月は判定せず空欄にし、False（判定できたが非該当）と区別する。

印は参考値で、ローカルだけの作業・マージ前・別の Organization の業務を区別できない。
本人に確かめるきっかけとして読み、シートの判定には使わない。1か月だけの該当はマージが翌月に
なっただけのこともあるので、続いているかは連続月数で読む。Claude Code analytics が月の途中
までの月は、下限に届いていないだけのことがある。

確かめて別の Organization の業務と分かった人は、members-info の
[GitHub ID の列](#github-id-の列email--github-login-の対応表)を `なし` にすると、その
members-info が採用される月では印が付かず、GitHub の対象の人からも外れる。対応表は月ごとに
その月の分析が採用した members-info から読むため、日付つきの members-info を残している組織
では、`なし` にする前のファイルが採用される月の印は残る。固定名の members-info だけの組織
では、次の分析ですべての月から消える。

`otel_data` は上から順に最初に当てはまる状態にする。`ok` 以外の月は、`otel_coverage` と
OpenTelemetry の件数の列をすべて空欄にする。

| 値 | 意味 |
|---|---|
| `not_configured` | OpenTelemetry を設定していない組織 |
| `spend_unconfirmed` | 始まっているスペースのどれかで、その月の spend が無いか、全月と確かめられない。キャッシュは読まない |
| `no_cache` | その月のキャッシュのファイルが無い |
| `unreadable` | キャッシュのファイルがあるが、読めない（形や語彙の不正、取得元の表や組織 UUID の設定との不一致など） |
| `ok` | 全月の spend を確かめられ、キャッシュを読めた |

`spend_complete` が True でも、単日の日付の命名の spend は期間を確かめられないため
`spend_unconfirmed` になる。`--allow-missing-workspace` で spend の無いスペースを需要 0 として
正式分析した月も `spend_unconfirmed` になる。

件数の列は、`otel_data` が `ok` で、`otel_coverage` が `ok` か `not_judged` の人だけが値を
持つ。spend にもキャッシュにも行が無い人の状態は `not_judged`。件数の列に値を持つ人のうち、
キャッシュにイベントが無い人の件数は 0 になる。

OpenTelemetry のイベントは product を区別しないため、Claude Code と同じ仕組みで動くほかの
product の利用が同じイベントとして届く場合、その分も値に含む。件数はキャッシュが区分に
分けたイベントの数で、区分に使う属性が付いていないイベントは `other` や既定の側に入るため、
属性が届いていない月の 0 は、利用が無かったことを意味しない。

## adoption-teams の列（チーム × 月の表）

人 × 月の表の行を、集まり（組織全体・部署・チーム）× 月へ畳んだ CSV。チーム・部署と組織
全体で、Claude Code の活用と GitHub の成果が月ごとにどう変わったかを読むための材料。前月比
などの変化は表に持たない。

置き場所と有効化は人 × 月の表と同じで、`adoption.enabled: true` のとき、正式分析のたびに
分析した組織ごとに、人 × 月の表とレポート（adoption-report）と一緒に
`reports/summary/adoption-teams-<YYYYMM>-<組織名>.csv` を書く（1組織だけの実行でも書き、
速報モードでは書かない）。月の範囲・各月の値の作り方・分析できない過去の月の扱いも人 × 月の
表と同じで、2つの表は同じ月の集合・同じ人 × 月の行から作る。GitHub 分析を有効にして
いない組織や OpenTelemetry を設定していない組織でも書ける。

読者は CTO と開発責任者を想定している。人 × 月の表と同じく、組織の担当者へ共有する成果物
の集合には含めず、考察の執筆（`discuss`）の資料にもならない。シートの判定には使わない
参考値で、ほかの成果物の内容はこの表の有無で変わらない。メールアドレス・repository 名・
login は書かない。

行は次のとおり。

- 1行が1つの集まりの1か月。`scope` が種別（`organization`＝組織全体・`department`＝部署・
  `team`＝チーム）、`name` がその名前（組織全体は空欄）
- 行は種別（組織全体・部署・チームの順）・名前・月の昇順に並べ、人数や量の多い順には
  並べない
- 組織全体は、その月にシートを持つ人の全員。シートを持つ人が0人の月も組織全体の行を書く
  （分析できずに飛ばした月と区別するため）
- 部署・チームは、その月の分析が採用した members-info の部署・チームの列で決める。過去の
  月の所属も、その月の分析が採用した members-info による（日付つきの members-info を月ごとに
  残していれば当時の所属になり、対象月より前のファイルが無い月は、後のファイルの所属になる）
- 兼務（`;` 区切り）の人は、それぞれの集まりに1人として入る（按分しない）。部署・チームが
  未記入の人は組織全体にだけ入る。このため、部署・チームの行の合計は組織全体と一致しない
- 部署・チームの行は、その月に1人以上いる集まりだけ書く。部署とチームに同じ名前があっても
  別の行になる

各列の意味は次のとおり。

- `scope` / `name` / `month` — 集まりの種別・名前と月（YYYY-MM）
- `spend_complete` / `github_data` / `github_cache_complete` — その月の値で、人 × 月の表の
  同名の列と同じ
- `seat_holders` — 集まりの人数（その月にシートを持つ人）
- `code_users` — その月に Claude Code のリクエストがあった人の数
- `code_users_3m` — その月を含む、暦で連続する3か月とも Claude Code を使った人の数。数える
  のはその月の集まりの人で、前の月の所属は問わない。前の月にシートを持たない人（前の月の
  行が無い人）は数えない。3か月のどれかが表に無い（入力に無い・分析できずに飛ばした）月は
  空欄
- `code_demand_usd` — Claude Code の需要（API 換算・USD）の合計
- `code_demand_median_usd` — シートを持つ人全員（使っていない人の 0 を含む）の Claude Code
  の需要の中央値
- `loc_median_of_users` — Claude Code を使った人（`code_users` に数えた人）の、Claude Code
  が加えた行の中央値（小数1桁）
- `github_people` — GitHub ID が `login` の人の数。GitHub 分析を有効にしていない組織は空欄
- `merged_pr_count` — login の人が作成し、その月に merge された PR の件数
- `pr_additions_median` — 同じ PR の追加行の中央値（1つの PR の大きさ。小数1桁）
- `lead_time_median_hours` / `lead_time_p90_hours` — 同じ PR の lead time の中央値と P90
  （小数1桁）。中央値は短い PR が多いと動きにくいので、遅い側を P90 で並べる
- `lines_added_capped` — login の人の、大きな変更を除いた追加行の合計
- `code_demand_usd_of_github_people` — login の人の Claude Code の需要の合計（行数が 0 の人も
  含める）
- `cost_per_merged_line_usd` — `code_demand_usd_of_github_people` ÷ `lines_added_capped`
  （小数4桁）。分母が 0 か、どちらかが空欄なら空欄
- `outside_org_people` — GitHub ID が `login` の人のうち、`outside_org` が True の人の数。
  login が0人か、login の人に判定が空欄の人が1人でもいれば空欄。`なし`・未記入の人は数えず、
  その人がいても空欄にはならない。該当した人を需要・マージ行・マージ行あたりの費用などの
  集まりの値から外さない
- `otel_data` — その月の OpenTelemetry の材料の状態（人 × 月の表と同じ）
- `otel_users` / `otel_excluded_people` — 使い方が見える人の数と、網羅率で除いた人の数
- `otel_active_days_median` / `otel_prompts_median` — 使い方が見える人の、使った日数と指示の
  回数の中央値（小数1桁）
- `otel_prompts` / `otel_requests` / `otel_subagent_requests` — 使い方が見える人の、指示の回数・
  リクエスト数・サブエージェント経由のリクエスト数の合計
- `otel_interactive_decisions` / `otel_interactive_decisions_asked` — 使い方が見える人の、確認の
  対象の判断の件数と、そのうち人が答えた件数の合計
- `otel_custom_subagent_users` / `otel_skill_users` / `otel_mcp_users` /
  `otel_custom_command_users` — 使い方が見える人のうち、自作のサブエージェントのリクエスト・
  スキルのリクエスト・MCP の判断・自作のコマンドの指示が、その月に1件以上ある人の数

合計と中央値は丸める前の値から出す（1人ずつ丸めて書いた人 × 月の表・usage-summary の値の
和とは、末尾の桁が違うことがある）。lead time と PR の大きさは、人ごとの中央値を平均せず、
その集まりの login の人が作った PR の集合から出す（人ごとの中央値は足し合わせられない
ため）。マージ行あたりの費用は、分子と分母を同じ人（login の人。行数が 0 の人も含める）で
取る。行数が 0 の人を外すと、使っていてマージの無い人が多い集まりほど費用が小さく出るため。

空欄になるのは次のとき。

- Claude Code の需要や行数、GitHub の値は、材料になる人の値が1人でも空欄なら、その集まりの
  その列は空欄にする（分からない値を 0 として数えない）。たとえば product の列が無い spend
  の月は Claude Code の列が、LoC の列を持つ code-analytics が無い月は
  `loc_median_of_users` が空欄になる。login の人の誰かの需要が空欄なら
  `code_demand_usd_of_github_people` と比率が空欄になる
- 中央値は、材料の人が 0 人なら空欄（使った人が 0 人の集まりの `loc_median_of_users` など）
- GitHub の列は、人 × 月の表と同じ状態の月だけ値を持つ。PR の列（`merged_pr_count` から
  `lead_time_p90_hours` まで）は `github_data` が `no_commits`・`no_previous_month`・`ok` の
  月、`lines_added_capped`・`code_demand_usd_of_github_people`・比率は `ok` の月だけ
- GitHub の対象の人（login の人）が0人の集まりは、`github_people` を 0 にして GitHub の値の
  列をすべて空欄にする（対象の人がいないことと、成果が0件だったことを区別する）。
  github-summary の組織全体の行はこの場合も PR を 0 件と書くので、組織全体の PR 数はこの
  場合だけ github-summary と一致しない
- PR が 0 件の集まりは `merged_pr_count` が 0 で、PR の大きさと lead time は空欄

GitHub の対象の人が1人以上いる月の、対象月の組織全体の行の PR 数・lead time の中央値と
P90 は、同じ実行の github-summary の組織全体の行と一致する。

OpenTelemetry の人数と件数は、`otel_data` が `ok` の月だけ値を持つ。使い方が見える人は、
その月の集まりの人のうち、次の3つをすべて満たす人。

- 人 × 月の表の OpenTelemetry の件数の列に値がある（`otel_coverage` が `ok` か `not_judged`）
- spend に Claude Code のリクエストがある（`code_requests` が 0 より大きい）
- OpenTelemetry のリクエストが1件以上ある（`otel_requests` が 0 より大きい）

`otel_coverage` が `low`・`missing`・`unknown` の人は、Claude Code の利用の有無を問わず、
網羅率で除いた人に数える。除いた人がいても、集まりの値は残りの人で出す。
OpenTelemetry の件数の列に値がある人の `code_requests` が1人でも空欄なら、
`otel_excluded_people` だけを書き、`otel_users` と残りの11列は空欄にする。使い方が
見える人が0人と決まった場合は、`otel_users` を 0 と書き、`otel_excluded_people` と合わせた
2つの人数以外は空欄にする。

1回の指示あたりのリクエストなどの量の比は列に持たず、集まりの件数の合計を分子と分母に
使って計算する。

人数の少ない集まりは、1人の動きで値が大きく振れる。閾値で隠さず人数（`seat_holders`・
`code_users`・`github_people`）を並べて出すので、値は人数と合わせて読む。値の大小から因果
（活用度が高い・低い）を断定する材料にもならない。

## adoption-report（レポート）

人 × 月の表とチーム × 月の表を、開いてそのまま読める1枚の HTML にしたもの。Claude Code の
活用と GitHub の成果が、組織全体・チーム・部署で月ごとにどう変わったかを見て判断するための
レポートで、主に読むのはチーム・部署の月ごとの変化。人ごとの値は参考として載せる。

置き場所と有効化は2つの表と同じで、`adoption.enabled: true` のとき、正式分析のたびに分析した
組織ごとに、2つの表と同じ実行で `reports/summary/adoption-report-<YYYYMM>-<組織名>.html` を
書く（1組織だけの実行でも書き、速報モードでは書かない）。設定はほかに無い。

読者は CTO と開発責任者を想定している。2つの表と同じく、組織の担当者へ共有する成果物の
集合には含めず、考察の執筆（`discuss`）の資料にもならない。シートの判定にも、人やチームの
評価にも使わない参考値で、ほかの成果物の内容はこのレポートの有無で変わらない。

レポートは新しい集計を持たない。載せる値は2つの表の値と、その列どうしの計算（割り算・
前月比・3か月比）だけで、どの値も同じフォルダの2つの CSV から検算できる。計算は CSV に
書いた字句（丸めた後の値）から行う。

節は上から次の順に並ぶ。冒頭に各節へのページ内のリンクを置く。

- 冒頭: 期間（最初の月 〜 最新の月）と注記（GitHub 分析の無い組織であること・行の無い月・
  途中の値の印の意味。当てはまるときだけ）
- 最新の月の要約: 組織全体の行の、Claude Code を使った人の数（シートを持つ人の数と並べる）・
  Claude Code の需要の合計・マージ行の合計・マージ行あたりの費用と、それぞれの前月比
- 組織全体: 月ごとの推移の折れ線（1つの図に1つの指標。Claude Code を使った人の数・需要の
  合計・Claude Code が加えた行の中央値・マージ行の合計・PR 数・マージ行あたりの費用）と、
  指標 × 月の数値の表。OpenTelemetry を設定した組織では、その場で確認した割合・
  サブエージェント経由の割合・自作のサブエージェントを使った人の割合の図も並べる
- チームごと・部署ごと: 集まりの一覧と、集まりごとの指標 × 月の数値の表。チーム・部署の行が
  無い組織ではその節を出さない
- 人ごとの一覧（参考）: 人 × 月の色の濃淡
- 人ごとの散布図（参考）: 最新の月の、Claude Code が加えた行 × マージ行と、Claude Code の
  需要 × マージ行
- 指標の読み方

数値の表では、指標を行、月を列にし、前月比・3か月比・推移の小さな線を添える。最初の14指標は
下の表のとおり。OpenTelemetry を設定した組織では、この後に OpenTelemetry の11指標を並べる。
「需要 / 人」「マージ行 / 人」「PR / 人」は、人数の増減の影響を除くため1人あたりで出す。
割り算は、分子か分母が空欄のとき・分母が 0 のときは値なし（「—」）。集まりの一覧には
「一覧」の欄が ○ の指標を、最新の月の値・前月比・3か月比・推移の小さな線で並べる。

| 指標 | 出し方（adoption-teams の列） | 変化 | 一覧 | 途中の値になる月 |
|---|---|---|---|---|
| シートを持つ人 | `seat_holders` | 差 | | なし |
| 使った人の割合 | `code_users` ÷ `seat_holders` | 差（ポイント） | ○ | 支出 |
| 3 か月続けて使った人の割合 | `code_users_3m` ÷ `seat_holders` | 差（ポイント） | | 支出 |
| 需要 / 人 | `code_demand_usd` ÷ `seat_holders` | 比 | ○ | 支出 |
| 需要の中央値 | `code_demand_median_usd` | 比 | | 支出 |
| 加えた行（中央値） | `loc_median_of_users` | 比 | ○ | 支出 |
| GitHub の対象 | `github_people` | 差 | | なし |
| うち成果が見えない人 | `outside_org_people` | 差 | | 支出 |
| マージ行 / 人 | `lines_added_capped` ÷ `github_people` | 比 | ○ | GitHub |
| PR / 人 | `merged_pr_count` ÷ `github_people` | 比 | ○ | GitHub |
| PR の大きさ | `pr_additions_median` | 比 | | GitHub |
| リードタイム 中央値 | `lead_time_median_hours` | 比 | ○ | GitHub |
| リードタイム 遅い 1 割 | `lead_time_p90_hours` | 比 | | GitHub |
| 費用 / マージ行 | `cost_per_merged_line_usd` | 比 | ○ | 支出・GitHub |

各列の意味は [adoption-teams の列](#adoption-teams-の列チーム--月の表)。

前月比と3か月比は次のとおり。

- 前月比は最新の月とその前の月、3か月比は直近3か月の平均とその前の3か月の平均を比べる
- 「差」は引き算。人数は小数1桁まで、割合はポイントの差で書く。その場で確認した割合の
  ポイントの差は小数1桁、それ以外の割合のポイントの差は整数。「比」は新しい方 ÷ 古い方 − 1
  の百分率
- 材料の値が1つでも無いとき・「比」で古い方が 0 のとき・材料に途中の値があるときは「—」に
  する。3か月比は6か月そろうときだけ出る。月の軸が6か月に満たない組織では、集まりの一覧に
  3か月比を書かない（数値の表の3か月比の列は残る）
- 変化の数字に、増減の良し悪しを表す色は付けない

途中の値の印は次のとおり。

- 支出レポートが月の途中までの月（組織全体の行の `spend_complete` が False）には `＊`、
  GitHub の収集が完了していない月（`github_cache_complete` が False）には `†` を付ける。
  付けるのは、数値の表と人ごとの一覧の月の見出し・図の月のラベル・要約と一覧の最新の値・
  散布図の見出しの月
- どの指標がどちらの月で途中の値になるかは上の表のとおり。シートを持つ人・GitHub の対象・
  OpenTelemetry の指標は途中の値にならない。途中の値が絡む前月比・3か月比は出さない
- 3か月続けて使った人の割合は、その月を含む3か月のどれかが `＊` の月なら途中の値として
  扱う（印は `＊` の月の見出しにだけ付く）
- 印のある月があるときだけ、冒頭に印の意味を書く

月の軸は、表の最初の月から最新の月までの暦の月を、間を空けずに並べる（古い月を省かない）。
年は最初の月と各年の1月に添える。表に行の無い月（入力の欠けで分析できずに飛ばした月）は
値なしの月として並べ、冒頭にその月を書く。数値の表では「—」、図では点を置かずに線を切り、
その月が絡む前月比・3か月比は出さない。

GitHub 分析を有効にしていない組織（チーム × 月の表のどの行も `github_data` が
`not_configured`）では、GitHub の指標（上の表の「GitHub の対象」以下）の要約・図・表の行・
一覧の列と、人ごとの一覧のマージ行・散布図・管轄外の検知の印と凡例・読み方の文を出さず、
冒頭にその旨を書く。

人ごとの一覧のマージ行の枠では、`outside_org` が True の月のセルに「!」を重ね、title 属性に
Claude Code が加えた行と連続して該当した月数を添える。セルの色はそのままで、印に良し悪しを
表す色を付けない。共通の凡例に「! Claude Code が加えた行があるのに、この Organization に
コミットも PR も無い月」を、指標の読み方に本人に確かめるきっかけとして読む旨を出す。GitHub
分析のある組織では、該当する人がいなくても凡例と読み方を出す。行数の下限はレポートには
書かない。数値の表の「うち成果が見えない人」は「GitHub の対象」の次に人数で出し、変化は差。
支出が月の途中までの月が材料にあれば前月比・3か月比を出さず、GitHub の収集が未完了の月は
値自体が空欄になる。集まりの一覧・最新の月の要約・図・散布図には足さない。

OpenTelemetry の指標は、組織全体・チーム・部署の数値の表で、活用と GitHub の指標の下に
区切りを入れて並べる。使い方が見える人は、支出レポートで Claude Code のリクエストがあり、
OpenTelemetry にもリクエストの記録があって、網羅率で除かれなかった人。届きが悪く除いた人は、
網羅率が低い・届いていない・確かめられない人。それより下の指標は、使い方が見える人で数える。

| 指標 | 出し方（adoption-teams の列） | 変化 |
|---|---|---|
| 使い方が見える人（OpenTelemetry） | `otel_users` | 差 |
| 届きが悪く除いた人 | `otel_excluded_people` | 差 |
| 使った日数（中央値） | `otel_active_days_median` | 比 |
| 指示の回数（中央値） | `otel_prompts_median` | 比 |
| 1 回の指示あたりのリクエスト | `otel_requests` ÷ `otel_prompts` | 比 |
| その場で確認した割合 | `otel_interactive_decisions_asked` ÷ `otel_interactive_decisions` | 差（ポイント、小数1桁） |
| サブエージェント経由の割合 | `otel_subagent_requests` ÷ `otel_requests` | 差（ポイント） |
| 自作のサブエージェントを使った人の割合 | `otel_custom_subagent_users` ÷ `otel_users` | 差（ポイント） |
| スキルを使った人の割合 | `otel_skill_users` ÷ `otel_users` | 差（ポイント） |
| MCP を使った人の割合 | `otel_mcp_users` ÷ `otel_users` | 差（ポイント） |
| 自作のコマンドを使った人の割合 | `otel_custom_command_users` ÷ `otel_users` | 差（ポイント） |

使った日数はリクエストのあった日数、指示の回数は人が入力したプロンプトの数。機能を使った人の
割合は、その月に1回でも使った人の割合。リクエストには要約や題名づくりなどの補助の呼び出しを
含めない。その場で確認した割合は、端末の対話で編集・コマンド・MCP を実行してよいかの判断の
うち、確認の画面で人が答えた分を数え、値を小数1桁で書く。

組織全体の推移には、次の3つの図を加える。分子を分母で割ってから100を掛けて描く。

| 図 | 値（adoption-teams の組織全体の行） |
|---|---|
| その場で確認した割合（%） | `otel_interactive_decisions_asked` ÷ `otel_interactive_decisions` × 100 |
| サブエージェント経由の割合（%） | `otel_subagent_requests` ÷ `otel_requests` × 100 |
| 自作のサブエージェントを使った人（%） | `otel_custom_subagent_users` ÷ `otel_users` × 100 |

集まりの一覧・最新の月の要約・人ごとの一覧・散布図には OpenTelemetry の指標を足さない。
OpenTelemetry を設定していない組織（チーム × 月の表のどの行も `otel_data` が
`not_configured`）では、OpenTelemetry の行・図・読み方を出さない。

量の比は合計同士の比なので、利用の多い人の使い方に引かれる。Claude Code と同じ仕組みで動く
ほかの製品（Cowork など）も使う人の値は、その分も含む。キャッシュの無い月と支出レポートが
全月と確かめられない月には値が無い。値なしは数値の表では「—」、図では点を置かずに線を切る。
月の状態と空欄の理由は、2つの表の `otel_data` と人 × 月の表の `otel_coverage` で読む。

集まりの一覧と数値の表は、最新の月の人数の多い順に並べる（同数は名前の順。最新の月に行の
無い集まりは後ろで、名前に添える人数は「—」）。一覧の先頭は組織全体で、名前からその集まりの
数値の表へ移れる。兼務の人はそれぞれの集まりに入る。人数の少ない集まりは1人の動きで値が
大きく振れるので、値は人数と合わせて読む。

人ごとの一覧は次のとおり。

- 1行が1人で、Claude Code の需要・Claude Code が加えた行・GitHub のマージ行（上限つき）の
  3つの枠に、月ごとの量を色の濃さで並べる（GitHub 分析の無い組織は前の2つ）
- 並びは部署（その人の最後の月の行の値。未記入は末尾）とメールの順で、量の多い順には
  並べない。メールはローカル部だけを出す
- 色は5段で、境目は固定（需要は 0 より大・50・200・1,000・3,000 USD、加えた行は 1・100・
  1,000・10,000・100,000、マージ行は 1・100・1,000・5,000・20,000。この値以上で1段濃くなる）。
  色の段は見た目の区切りで、載せる行や数え方を変えないので、設定には置かない
- 0・値なし（材料なし）・GitHub ID が login でない人（「–」）・その月にシートを持たない人
  （空白）・行の無い月（全員に「×」）は、色の段と別の見た目にする
- セルの値はセルに重ねると出る（title 属性）。負の値（需要は負になりうる）は、図と色の段では
  0 の位置に置き、数値の表と title 属性には負の値のまま出す

人ごとの散布図の点は、最新の月に、その図の横軸とマージ行の両方に値のある人（値が 0 の人は
置き、値なしの人は置かない）。目盛りは対数で、0 も置ける。

過去の月の所属（部署・チーム）は、その月の分析が採用した members-info による（チーム × 月の
表と同じ）。

JavaScript を使わず、外部への通信もしない（フォント・画像・スタイルシートも読み込まない）
ので、ブラウザで開くだけで全内容が読める。配色は閲覧する環境の設定（明るい配色・暗い配色）に
従い、切り替えの部品は置かない。月が増えて幅に収まらない表は、枠の中で横にスクロールする。

## 複数スペース（workspace）の組織の成果物

`config.yaml` の `organizations.<組織名>.workspaces` が 2 つ以上ある組織では、
組織 1 セットの成果物に全スペースのアカウントを載せる。サマリの対象メンバー数は
「人数（アカウント数）」とし、「スペース別」表に各スペースのシート構成・費用・需要を示す。
件数（一次判断や変更推奨など）はアカウント単位。複数組織の横断サマリでも
「人数（アカウント数）」を使う。月中の推移などは表示名つきの見出しでスペースごとに出る。

判定系の全アカウント表では、複数アカウントを持つ人の主の行を全スペースの合算需要で
判定する。したがって、この表の需要を縦に足すと副の分が二重になる。観測系の
詳細利用状況、スペース別表、人別の利用では各アカウント自身の需要を使い、
人の需要は全アカウントの和として示す。

report の「複数スペースの利用」には、副のシートを持たない人の払い出し判定、
副にシートを持つ人の継続判定、副を持ちながら主で実課金が発生した人の一覧がある。
払い出し判定は主の実課金を副の損益分岐 `secondary_breakeven_usd`（`organizations.<組織名>`
直下のキー。`workspaces` の中ではない）と比較する。
対象月に主の上限へ到達した場合、または必要な連続月数の実課金が損益分岐以上なら
「候補」（連続月数は対象月から暦で連続し全月そろった月だけを数え、欠月・部分月で
途切れる）。主の追加クレジットが無効の人、有効かどうか分からない人（上限が未記入で
実課金も観測されていない）、主のシートが払い出すシート種別と違う人は「判断材料なし」。
それ以外で実課金があれば「観察」、なければ「不要」。
継続判定は副の需要を損益分岐と比較する。以上なら「継続」、払い出し後の月（対象月から
暦で連続し、副で全月そろった月）が `evaluation_months` に満たなければ「データ蓄積待ち」、
必要月数すべてが損益分岐未満なら「戻す候補」、それ以外は「観察」。損益分岐の既定は
副の固定シートの価格。
主で実課金が出た人の一覧は判定ではなく、副への切り替え状況を月別の副の需要と
突き合わせて読むための事実。詳しい読み方は report 内の凡例にある。

details には「人別の利用」、dashboard には「複数スペース」タブが加わる。
details には副ごとに「主と副の切り替え」も加わる（主と副で終了日が2つ以上一致する月で、
対象者がいる場合だけ）。区間は、終了日が一致した月初からの累積の差で作る。
上限に当たった時刻や切り替えた時刻は表から分からない。
recommendations と usage-summary の CSV には email の次に `workspace` 列が入り、
ディレクトリ名で各アカウントを区別する。V2 の decision-evidence の列は
[decision-evidence の列](#decision-evidence-の列v2-判定)を参照。

速報の preview と preview-dashboard では「スペース別」「人別の需要（スペース合算）」を
出し、一次判断テーブルにスペース列を足す。主の行の需要は全スペースの合算、
スペース別と人別の需要は各アカウント自身の観測値と月末ペース換算を使う。
固定シートの副アカウントは一次判断の対象外。ただし利用がほぼ無ければ遊休候補として
示す。速報には副の払い出し判定・継続判定を置かず、正式分析で行う。
入れ子の組織の速報は全 workspace で観測日数が同じ必要があり、ファイル名から分かる日数が
違えば `--days` を付けても止まる。

### 設定（config.yaml > organizations.<組織名>.workspaces）

- `primary` — 主スペースだけを `true` にする
- `label` — 成果物に出すスペースの表示名（省略時は workspace 名）。組織内で一意にする。
  重複は設定の読み込みでエラーになる
- `fixed_seat` — 運用方針で固定するシート種別。副スペース（複数 workspace の組織）のための設定。
  指定された workspace のアカウントはシートの判定と追加クレジットの提案の対象外。
  その workspace に固定と違うシート種別のアカウントがあると
  警告が出る（判定は変えない）
- `credit_limit_default_usd` — 副アカウントの追加クレジット上限の既定
- `evaluation_months` — 払い出し判定と継続判定に必要な連続月数（省略時は `decision.hysteresis_months`）

## 追加クレジット（usage credits）の上限

Team プランの各シートには利用の込み枠（レート制限型）があり、組織やユーザ設定で「追加
クレジット」（枠超過時の従量課金）を有効化できる。上限はユーザごとに管理画面で設定される。
この設定はエクスポート CSV に含まれないため、`members-info.csv` の追加クレジット上限の列に
手入力する。複数スペースの組織では、副アカウントの上限は `credit_limit_default_usd` を既定とし、
主アカウントは従来どおり members-info の列を使う。列の値の意味は次のとおり:

- 正の数値（`$` やカンマ可）: その金額を上限に従量課金が有効
- `0`: 無効（枠超過分は課金されず、需要は上限で頭打ちになる）
- `無制限` / `unlimited` / `inf` / `∞`: 上限なしで有効
- 空欄: 不明。サマリの追加クレジットの構成・recommendations の `credits_mode`・v1 の上限フラグの
  抑止では、当月までに実課金が観測されていれば有効と自動確定する

V2 の判定は記入された上限で分岐し、空欄は実課金があっても不明のまま扱う。
`0` と書いてあっても対象月に実課金があれば、記入と観測の食い違いとして不明に扱う。

上の4語以外は数値として解釈する。数値として受けるのは半角の数字（符号・小数点・4 桁までの指数）に
`$`・`＄` と桁区切りのカンマが付いた形だけで、全角数字（`２５０`）・円記号を含む値（`￥1,500`）・
桁区切りに `_` を使った値（`1_0`）・`Infinity` や `1e309` のような非有限の値・負値は「不明」として
警告に載せる。

クレジットの有無で分析の見方が変わる。有効なユーザは超過分が実課金（spend の net_spend）として
観測されるため、実課金がセンサーとして働く。v1 では実課金ゼロなら枠内と判断でき、上限到達疑いの
フラグは付けない。無効なユーザは超過需要が課金に表れず、絞り（throttle）として観測不能に
なるため、v1 の「Standard時/Premium時」の枠超過分は実際には請求されない「絞り負担のドル換算」
（需要が上限で抑えられる分の目安）である点に注意する。

追加クレジット上限を入れておくと、正式分析・速報に次が加わる（列が空・実課金ゼロなら従来どおり）:

- サマリに追加クレジットの構成（有効/無効/不明の人数・上限の合計）
- 上限到達（実課金が上限に迫る）・整合性の警告（上限を超過している/無効なのに課金がある）
- シートが吸収した量の実測（E = API換算需要 − 実課金）の分布。E は各ユーザの容量の下限を示す
  （上限は分からないため、E が小さいことは容量に余裕がないことを意味しない）
- 速報では、有効ユーザの残額と到達見込み（観測実課金ペースの線形外挿による目安）

正式分析の付与候補は判定の版で異なる。

- 既定の v2 は「上限つき付与」と「設定確認」の2段で示す。上限つき付与は、追加クレジットが
  無効の Standard ユーザで対象月の需要が方針線以上だが継続していない人。推奨初期上限は
  `usage_credits.grant_suggested_cap_usd`（既定 $150）で、提示に使うだけで判定には使わない。
  設定確認は、追加クレジットの設定が不明の Standard ユーザで実課金か需要が昇格の水準の人。
  report の節はどちらかに該当者がいるときだけ出し、dashboard のカードは固定シートでない
  主 workspace に常に出す（各段に該当者がいなければ「該当者なし」）
- v1 は、昇格の前に上限つきクレジットを付与して1ヶ月の課金実測で判断すべきユーザを付与候補に
  する。dashboard では固定シートでない workspace にカードを常に表示し、候補がいない場合は
  「該当者なし」と「判定不能（上限が未記入）」を区別する。推奨初期上限の設定は v2 と同じ

## GitHub 分析の有効化（config.yaml > organizations）

GitHub の情報（PR 数・リードタイム・コミット単位の行数）を参考値として使うかどうかは
組織ごとに決める。`organizations` に書いた組織だけが対象で、書かない組織は GitHub 関連の
処理と警告から一切除外される。

```yaml
organizations:
  example:
    github_org: example-org
```

キーは入力ディレクトリ直下の組織名、値はその組織の GitHub Organization 名。両者は
一致しない前提の対応表なので、名前が同じ組織でも省略はできない。`organizations` の
直下だけは既定に無いキー（組織名）を書けるが、その中身に書けるのは `github_org`・
`workspaces`・`secondary_breakeven_usd`・`claude_export`・`otel` だけで、`github_org` の値が
GitHub の Organization 名として読めなければ設定の読み込みでエラーになる。

### GitHub ID の列（email → GitHub login の対応表）

PR とコミットの行数を誰の実績として数えるかは、`members-info.csv` の `GitHub ID` 列が
決める。GitHub の API から email は取れないため人手で記入する列で、有効にした組織だけが
使う。値は3種類:

| 値 | 意味 |
|---|---|
| 空欄 | 未記入。未対応として扱い、doctor が記入を促す |
| `なし` / `none` / `-` | 対象の GitHub Organization で開発しない人（PR も作らず、コミットもしない）。未対応として扱うが警告しない。月々の PR の有無で書き換える値ではなく、開発する場所が変わったら login を書く |
| それ以外 | GitHub の login（英数字で始まり英数字で終わる 1〜39 文字。区切りに使えるのは連続しないハイフンと高々 1 個のアンダースコア） |

自分で PR を作らず、他の人の PR にコミットする人も login を書く。

login として読めない値は未対応として扱い、写し間違いに気付けるよう warning に出す。
email の重複と login の重複（大文字小文字を区別しない）は error で、対応表としては
読まない（別人の PR を帰属させたまま集計が完走しないようにするため）。日付つきの
members-info を置いている組織では、対象月の月末以前で最新のファイルの列を読む。

有効にした組織では `seat-analyzer doctor` が次を検査する。読み取りだけを行い、PR も
repository も取得しない。

- GitHub CLI（`gh`）で認証できているか。できていなければ error
- token の権限（`read:org` と `repo`）が足りているか。足りなければ error。権限を
  機械的に確認できない token（fine-grained PAT・GitHub App）では判定しない
- 設定した Organization を参照できるか。参照できない場合と、SAML SSO の承認が要る
  場合を区別して error
- GitHub API の利用上限に達していないか。達していれば warning（再実行で解消する）
- `input/<組織名>/members-info.csv` の `GitHub ID` 列（email → GitHub login の対応表）の
  有無と中身。ファイルが無い場合・列が無い場合・シートを持つメンバー（github-summary の
  対象者と同じ定義）に対応づかない人が居る場合は warning、対応表そのものが壊れている
  場合は error（誤った対応で集計を完走させない）

`organizations` に書いた組織名が入力の組織ディレクトリのどれとも一致しない場合は、
`=== 設定検査 ===` として warning を出す。綴り違いで検査が黙って全部飛ぶのを防ぐため。

### github-cache（collect が作るキャッシュ）

`seat-analyzer collect --org <組織名> --source github --month YYYY-MM` は、対象月に merge
された PR のメタデータを `input/<組織名>/github-cache/prs-YYYY-MM.json` に保存する。
1ファイル = 1組織 × 1月で、PR は merge した日時（UTC）の月に帰属する。ツールが読み書きする
ファイルで、手で編集する前提ではない。

形式は schema 2。PR 1件につき保存するのは次の項目だけ。title・本文・レビュー本文・
変更ファイル・diff・コミットのメッセージ・作者の名前・ブランチ名・コードは取得も保存もしない。

| 項目 | 内容 |
|---|---|
| `repository` | repository 名（Organization 名は含まない） |
| `number` | PR 番号 |
| `author_login` | 作成者の GitHub login（削除済みのアカウントは空） |
| `author_type` | 作成者の種別（`User`・`Bot` など。同上） |
| `created_at` | 作成日時（UTC） |
| `merged_at` | merge 日時（UTC） |
| `additions` | 追加行数 |
| `deletions` | 削除行数 |
| `is_draft` | draft かどうか |
| `merge_commit_oid` | PR のマージで作られたコミットの SHA（無ければ null） |
| `commit_count` | PR に含まれるコミットの総数（GitHub の `totalCount`） |
| `commits` | PR に含まれるコミットの配列（下表） |

コミット1件につき保存するのは次の7項目だけ。

| 項目 | 内容 |
|---|---|
| `oid` | コミットの SHA（40桁の小文字の16進） |
| `author_login` | 作者の GitHub login（アカウントに結び付かなければ null） |
| `author_email` | 作者のメールアドレス（原文の大小・空文字列を保つ。作者かメールが無ければ null） |
| `additions` | 追加行数 |
| `deletions` | 削除行数 |
| `committed_at` | コミット日時（UTC） |
| `is_merge` | 親が2つ以上のマージコミットかどうか |

`commits` は `(committed_at, oid)` の昇順で、同じ PR 内の SHA の重複はエラーにする。
1回で取り切れない PR は PR ごとに続きを辿るが、GitHub は PR のコミットを250件までしか
返さない。保存件数は `commit_count` と一致するか、総数が250を超えるときは250件と一致する。
続きの取得やコミットの解釈・件数の整合に失敗したら、その PR を含む期間全体を未完了にする。
Bot・draft の PR のコミットも保存する。コミットの行数は github-summary で集計する。
`author_email` は集計に使わない。

schema 1 のキャッシュも読めるが、コミットの材料は無い（`commits`・`commit_count`・
`merge_commit_oid` は読み取った値では None）。次の収集では PR と完了済みの期間を引き継がず、
その月の全期間を取り直して schema 2 で書く。repository の一覧も今回の一覧で書き直す。

PR を指すキーは `repository#番号`（例: `repo-a#12`）で、同じ PR を2度保存しない。
repository 名の大文字小文字は区別せず同じ1つとして扱う。

`repositories` には収集した時点の repository の一覧（archived / fork / template を除いた
名前と、除いた件数）が入る。分析はこの一覧を集計の対象として読むので、`gh` もネット
ワークも呼ばずにキャッシュだけで参考値を出せる。一覧を保存する前に作られたキャッシュは
そのまま読めるが github-summary の材料にはならないので、収集をもう一度実行して一覧を
付ける。

`complete_windows` は「読み切れて、かつ期間の終わりから1日が過ぎた」期間の一覧。月は
1–7 / 8–14 / 15–21 / 22–28 / 29–月末 の固定の期間に分けて収集し、この一覧に入っていない
期間は次回の実行で取り直す。1日の猶予を置くのは、検索の反映遅れで日付境界の PR を
取りこぼさないため。したがって対象月の全期間が揃うのは翌月2日以降になる。

読み込みは厳密で、形式の版・組織名・対象月が合わないファイル、定義外のキーを持つ
ファイル、キーと内容が食い違うファイルはエラーにする（別の組織のキャッシュや、項目を
足したファイルをそのまま集計へ渡さないため）。エラーが出た場合はそのファイルを別の場所へ
移してから収集し直す。

## claude.ai からの CSV 取得（config.yaml > claude_export）

`seat-analyzer collect --source claude` の設定と、取得したファイルの扱い。使い方は
[usage.md](./usage.md) の「claude.ai からの CSV 取得」、初回の設定は [setup.md](./setup.md) の
「claude.ai からの CSV 取得を設定する」。既定は不活性で、組織（または workspace）の区画に
`org_id` を書いたものだけが取得の対象になる。

### 共通の設定（トップレベルの claude_export）

| キー | 既定 | 内容 |
|---|---|---|
| `chrome_path` | `""` | Chrome の実行ファイル。空文字なら OS ごとの既定の場所を探す。書くときは絶対パス（`~` 可） |
| `profiles_dir` | `~/.seat-analyzer/profiles` | 専用プロファイルの置き場。配下の `<profile>` ディレクトリが 1 アカウント |
| `staging_dir` | `~/.seat-analyzer/exports` | Chrome のダウンロード先（取得の一時置き場）。検証の後に `input/` へコピーする |
| `timeout_minutes` | `15` | 取得の完了を待つ上限（分）。`--timeout` を付けた実行ではそちらが優先 |
| `login_warning_days` | `3` | `--check-login` で「期限間近」にする残り日数（0 以上の整数）。Cookie の期限までの日数がこれを下回ると期限間近（終了コード 1）。0 なら期限を過ぎたものだけ。確認の間隔 + 対応の猶予で決める（日次なら 3・週次なら 10 など。週次は 7 日 + 猶予 3 日） |

`profiles_dir`・`staging_dir` の相対パスは、`paths` と同じくそれを書いた設定ファイルの
置き場所が基準になる（`~` はホームディレクトリに展開し、絶対パスはそのまま使う）。
`chrome_path` は設定ファイルの置き場所で解決しないので、絶対パスか空文字で書く（相対パスは
設定の読み込みでエラーになる）。空文字のときに探す場所は、macOS が
`/Applications/Google Chrome.app`、Windows が Program Files・Program Files (x86)・
LocalAppData の下の `Google\Chrome\Application\chrome.exe`、それ以外が PATH 上の
`google-chrome`・`google-chrome-stable`・`chromium`・`chromium-browser`。

### 組織・workspace の区画

単一スペースの組織は `organizations.<組織名>.claude_export`、複数スペースの組織は
`organizations.<組織名>.workspaces.<workspace名>.claude_export` に書く。

| キー | 内容 |
|---|---|
| `profile` | 使うプロファイル名（英数字と `.` `_` `-`。`.` と `..` は使えない）。`--setup`・`--finish-setup`・`--login`・`--list-orgs`・`--check-login` に渡す名前と揃える |
| `org_id` | claude.ai の組織 UUID（8-4-4-4-12 桁の16進。`--list-orgs` で調べる） |
| `kinds` | 取得する種別（`members` / `spend` / `code` から重複なく 1 つ以上。省略時は 3 種すべて） |

```yaml
organizations:
  example:
    claude_export:
      profile: corp
      org_id: 00000000-0000-4000-8000-000000000001
      kinds: [members, spend, code]
  example2:
    workspaces:
      main:
        primary: true
        claude_export:
          profile: corp
          org_id: 00000000-0000-4000-8000-000000000002
      second:
        claude_export:
          profile: corp
          org_id: 00000000-0000-4000-8000-000000000003
```

設定の読み込みで次をエラーにする。

- `org_id` が UUID の形でない、`profile` が名前の規則に合わない
- `kinds` に 3 種以外の値や重複がある、空のリストである（`org_id` を書かない区画でも検査する）
- `org_id` を書かずに `profile` や既定と違う `kinds` を書いた区画（有効にしたつもりの設定を
  黙って不活性にしない）
- `workspaces` を持つ組織の直下の区画（どの workspace へ置くかが決まらない）
- 同じ `org_id` を 2 か所に書いた（大文字小文字の違いも同じ UUID とみなす）
- 未知のキー

取得の計画を作る時点で、大文字小文字や文字の合成の違いだけの組織名（同じ組織の workspace
名どうしも）を止める。それを区別しないファイルシステムでは同じディレクトリになるため。

### コマンドのオプション（collect --source claude）

| オプション | 内容 |
|---|---|
| `--month YYYY-MM` | 実行機のローカル日付で決まる当月か前月（それ以外はエラー）。省略時は当月 |
| `--org <組織名>` | 取得する組織（複数指定可）。省略時は設定した全組織 |
| `--profile <名前>` | 使うプロファイルで対象を絞る |
| `--dry-run` | 計画を表示して終了する（ブラウザを起動しない）。取得できる時期の前や期間を過ぎたときは、計画の代わりに理由を表示する |
| `--keep-browser` | 取得の後も Chrome を終了させない |
| `--timeout <分>` | 取得を待つ上限 |
| `--import <run_id>` | staging に残った実行の検証と配置だけをやり直す（ブラウザを起動しない） |
| `--setup <名前>` | 専用プロファイルを作って Chrome をログイン画面で起動し、人が行う手順（ログイン・拡張機能の読み込み）を表示して終わる（待たない） |
| `--finish-setup <名前>` | `--setup` の後、人の操作が終わってから実行する。そのプロファイルの Chrome を終了させ、拡張機能が同梱の場所から読み込まれていて有効であることを確かめてからプロファイルの設定を書く |
| `--login <名前>` | 実行ページの「ログインし直す」を人が押すと、拡張機能がそのプロファイルのセッションの Cookie（名前が `sessionKey` で始まるもの）を消してから、claude.ai のログイン画面を開く（終了は待たない。ロックは取らない） |
| `--list-orgs <名前>` | アカウントが参加している組織の uuid・name・rate_limit_tier・plan を表示する |
| `--check-login [<名前>]` | ログインセッションの状態（有効・期限間近・無効・不明）を表示する。名前を省くと `claude_export` を設定した全プロファイルを初出順に確かめる（名前を指定すれば設定に無いプロファイルでもよい） |

`--setup`・`--finish-setup`・`--login`・`--list-orgs`・`--check-login`・`--import` は単独で使う
（`--list-orgs` と `--check-login` だけは `--timeout`・`--keep-browser` を併用できる）。これらと
`--profile`・`--dry-run`・`--keep-browser`・`--timeout` は `--source github` では使えない。
`--source otel` で使えるのは、このうち `--dry-run` だけ。
組み合わせの誤りは終了コード 2。

終了コードは、対象のすべての (組織, 種別) を配置できたときだけ 0。1 件でも失敗・時間切れが
あれば 1。ただし、取得できる時期の前や UTC が先に翌月へ進んだため取得しない場合は、`--month`
省略時は 0、指定時は 1（`--dry-run` も同じ）。時期の規則は [usage.md](./usage.md) の
「claude.ai からの CSV 取得」を参照。各プロファイルの起動直前にも判定し、2 つ目以降で時期を
外れた場合や、ローカル日付が変わって計画のモード・月と合わなくなった場合は、そのプロファイルを
失敗として終了コード 1 にする。`--check-login` は、確かめた全プロファイルが有効のときだけ
0（期限間近・無効・不明・時間切れのほか、設定が済んでいない、拡張機能が使えない、または使用中の
プロファイルがあれば 1）。

同じプロファイルを 2 つの実行が同時に使わないよう、取得・`--list-orgs`・`--check-login`・
`--finish-setup`・`--import` はその間 `<staging_dir>/<profile>.lock` に OS のファイルロック（Unix は flock、Windows は
msvcrt.locking）を取る。別の実行がロックを持っていれば、そのプロファイルは使用中として止める
（取得では、そのプロファイルの実行だけを失敗にする）。ロックは実行が終わると（異常終了を
含めて）外れるので、ロックファイルを消す必要は無い（ファイルは空のまま残る）。拡張機能の側も、同じ Chrome で別の実行が進行中なら新しい実行を始めない
（開始から 1 時間を超えた記録は無視する。何も書かない `--login` はこの対象外で、ログイン待ちで
止まった取得が残っていても実行できる）。

Chrome を終了させるのは、プロファイル（`--user-data-dir`）が一致し、かつ実行ファイルが
起動に使ったものと一致するか名前に chrome / chromium を含むプロセスだけ（Linux の
`google-chrome` はラッパースクリプトで、プロセスには実体の `chrome` が見えるため。同じ
プロファイルを引数に持つ別のプログラムは終了させない）。穏当に終了を求めて残ったものを
強制終了する前に列挙し直し、まだ一致しているものだけを対象にする。

### staging の配置

1 回の取得（プロファイル 1 つ）ごとに `<staging_dir>/<run_id>/` を作る。`run_id` は
`<profile>-<current|previous>-<YYYYMMDD-HHMMSS>`（組織一覧は `<profile>-list-orgs-<...>`、
ログインの確認は `<profile>-check-login-<...>`。ローカル時刻）。`--login` も
`<profile>-login-<...>` を拡張機能へ渡すが、実行ディレクトリは作らず、拡張機能も何も書かない。

```text
<run_id>/run.json                           コマンドが起動の前に書く、その実行の計画（--import が使う）
<run_id>/progress.json                      拡張機能が各手順の後に上書きする途中経過
<run_id>/session.json                       拡張機能が書くログインセッションの観測（--check-login のときと、取得で manifest の前）
<run_id>/manifest.json                      拡張機能が最後に書く結果（コマンドはこれを待つ）
<run_id>/<dir>/<kind_dir>/<元のファイル名>  ダウンロードした CSV
<run_id>/orgs.json                          --list-orgs のときの組織一覧
<profile>.lock                              OS のファイルロックの対象（空のまま残る。staging の直下）
```

`dir` は `<組織名>` か `<組織名>/<workspace名>`、`kind_dir` は `members`・`spend`・
`code-analytics`。manifest の結果は計画の (配置先, 種別) と突き合わせるだけで、配置先の
パスは常に設定から組む（計画に無い結果は捨て、計画にあって結果の無い組み合わせは失敗に
する）。`--import` は run.json から計画を組み直し、その実行の対象月で検証する。run.json の
対象が設定に無いか、UUID が設定と違えば配置しない。

専用プロファイルの設定（`Default/Preferences`）に `--finish-setup` が書くのは、claude.ai からの
自動ダウンロードの許可・ダウンロードの確認を出さないこと・ダウンロード先（staging）だけで、
他の項目は保つ（書き換えるときは元の内容を `Preferences.bak` に残す）。書く前にその
プロファイルの Chrome を終了させ、動いている間は書かない。拡張機能の読み込みは
`Default/Secure Preferences` と `Default/Preferences` の拡張機能の設定で確かめる。同梱の場所から
読み込まれていないか、無効になっていれば書かずに止める。無効かどうかは、Chrome が拡張機能の
項目に記録する無効の理由で判定する。取得の前には、ダウンロード先が staging を指していることと、
拡張機能が同梱の場所から読み込まれていて有効であることを確かめる。条件を満たさなければ
`--setup` と `--finish-setup` を案内して起動しない（`--check-login`・`--login`・
`--list-orgs` も同じ）。

### ログインセッションの判定

`--check-login` では、拡張機能が claude.ai を開いてページの状態を 1 秒ごとに最大 20 秒見る
（アプリかログイン画面に定まったら打ち切る。外部セキュリティ検証は人の操作なしに解ける
ことがあるので上限まで見直す）。アプリが表示されたときだけ `/api/organizations` を 1 回読み
（上限 10 秒）、セッションの Cookie（`sessionKey`）の期限と合わせて `session.json` に書く。人の
操作は待たない。通常の取得でも manifest.json の前に Cookie の期限だけを同じ形で書く（ページと
API は見ないので `page`・`api` は null）。どちらも Cookie の値は書かない。

| 項目 | 内容 |
|---|---|
| `run_id` | 実行の識別子（コマンドはその実行のものかを確かめる） |
| `checked_at` | 観測した時刻（ISO 8601・UTC） |
| `cookie_found` | セッションの Cookie があったか |
| `cookie_expires_at` | Cookie の期限（ISO 8601・UTC）。期限の無い Cookie が混じれば null、複数あれば最も早いもの |
| `page` | `app`・`login`・`challenge`（上限まで外部セキュリティ検証のまま）・`unknown`（一度も読めなかった）。通常の取得では null |
| `api` | `{ok: true, status, organizations}`（組織は件数だけ）か `{ok: false, status, reason}`（応答が無ければ status は null）。読んでいなければ null |
| `log` | 実行ページのログ |

壊れた JSON・項目の欠落・形の違う値（タイムゾーンの無い日時を含む）は読めないものとして
扱う（`--check-login` は待ち時間の上限の後にその理由を表示して失敗、通常の取得は警告を 1 行
出すだけで結果を変えない）。

状態は上から順に最初に当たったものを採る。

1. `page` が `login` → 無効
2. API の読み取りが HTTP 401 → 無効
3. `page` が `challenge`・`unknown`（取り決めに無い値を含む）、API の読み取りに失敗（403 を
   含む 401 以外と、応答なし）、`page` が `app` なのに API の結果が無い → 不明
4. Cookie が無い・Cookie の期限が無い → 不明
5. 残り日数が `login_warning_days` を下回る → 期限間近（0 なら期限を過ぎたものだけ）、
   それ以外 → 有効

残り日数は Cookie の期限までの時間を 1 日単位で切り捨てた整数で、表示（「あと n 日」。0 は
「あと 24 時間未満」、負は期限経過）と `login_warning_days` との比較に同じ値を使う。期限は
実行機のローカル時刻で表示する。

### 配置前の検証

ダウンロードしたファイルごとに次を確かめ、最初に外れた理由を表示して配置しない（ファイルは
staging に残る）。

1. ファイルがあり、空でない
2. 先頭行（64 KiB まで）のヘッダに、種別ごとの必須の列がある。照合は `columns.<種別>` の
   エイリアスと、分析の読み込みと同じ正規化で行う
   - メンバー一覧: email・シート種別
   - 支出レポート: email・model・prompt_tokens・completion_tokens
   - Claude Code analytics: email と月間の LoC（支出レポートとの取り違えを止める）
3. メンバー一覧と支出レポートは、ファイル名に組織 UUID の形が含まれていれば、それが設定の
   `org_id` と同じ（大文字小文字は区別しない）。拡張機能の組織の確認をすり抜けた別組織の
   ファイルを止める（Claude Code analytics のファイル名には UUID が入らないので見ない）
4. ファイル名の期間が対象月に合う
   - 支出レポート: 期間付きで、開始が対象月の 1 日、終了が対象月の末日以前
   - Claude Code analytics: 期間付きで、開始が対象月の 1 日（終了日は部分月でも月末日に
     なるので見ない）
   - メンバー一覧: スナップショットの日付が対象月の 1 日以降（前月モードでは取得した日＝
     翌月の日付になる）

通ったファイルは元のファイル名のまま入力の種別ディレクトリへコピーする（同名は上書き）。
組織ディレクトリ（入れ子レイアウトなら workspace のディレクトリ）が無ければ作らずに配置しない。

例外として、当月モードの Claude Code analytics は、ファイル名の期間の終了日を取得日に置き換えた
名前で置く（置き換えるのは年月日の数字だけで、区切りとそれ以外の文字は保つ）。終了日は
スナップショットの時点として使われ（月中の Claude Code 活動）、claude.ai のエクスポートは部分月
でも終了日が月末日になるため。取得日は run.json の `created_at` と同じ時刻の UTC の日付（同じ
実行のメンバー一覧のファイル名の日付と揃う）で、`--import` も run.json の `created_at` の UTC の
日付を使う（取り込む日ではない）。`created_at` が無いかタイムゾーン付きの ISO 8601 でなければ
`--import` は配置せずに止まる。取得日が期間の外か終了日と同じとき、前月モード、メンバー一覧と
支出レポートは元のファイル名のまま。staging のファイルの名前は変えない。

## OpenTelemetry の取得（config.yaml > organizations.<組織名>.otel）

`collect --source otel` は有効にした組織のイベント表を、人 × 日（UTC）× 集計名 × 区分に
集計して取得する。設定は組織単位で、複数スペースでも `otel` は組織直下に書く。

| キー | 内容 |
|---|---|
| `organizations.<組織名>.otel.bigquery.project` | 問い合わせを実行する project。未指定は空文字 |
| `organizations.<組織名>.otel.bigquery.dataset` | イベント表の dataset。未指定は空文字 |
| `organizations.<組織名>.otel.bigquery.logs_table` | イベント表の名前。未指定は空文字 |
| `organizations.<組織名>.otel.organization_ids` | 絞り込む claude.ai の組織 UUID のリスト。未指定は空 |
| `otel.maximum_bytes_billed` | 読み取り量の上限（byte）。真偽値を除く1以上の整数。既定は 2000000000 |

3つの表名はすべて必要で、英数字と `_`・`-` の1字以上。3つとも空で UUID も空なら無効
（`otel: {}` も同じ）。UUID だけの指定では有効にできない。

絞り込みの UUID は、`otel.organization_ids` が空でなければその値を使う。空なら、組織直下の
`claude_export.org_id` と各 workspace の `claude_export.org_id` の空でない値を、記述順に
重複なく集める。どちらも無ければ有効な `otel` の設定はロード時にエラーになる。
UUID は8-4-4-4-12桁の16進数で、大小文字を区別せず小文字にそろえる。明示指定での重複は
エラー。指定と一致しない・空の `organization.id`、メールアドレスが空のイベントを除外し、
それぞれの件数を記録する。

失敗時は終了コード1で理由を標準エラーに表示し、キャッシュを書かない。

| 失敗 | 対処 |
|---|---|
| `bq` が見つからない | Google Cloud SDK を導入し、PATH に `bq` を置く |
| 認証が無い・切れている | `gcloud auth login` を実行する |
| project・dataset・表が無い、または権限が無い | 表の場所、表を読む権限、project で問い合わせを実行する権限を確かめる |
| 応答が無い | 接続と BigQuery の状態を確かめて再実行する（定義は60秒、問い合わせは600秒で打ち切る） |
| 必須列が無い | 表の形を確かめる。最上位の `timestamp`（TIMESTAMP）と `labels`（RECORD）配下の `event_name`・`user_email`・`organization_id`・`session_id` が必要 |
| 読み取り量が上限を超える | `--dry-run` の見積もりと課金を確認し、必要なら `otel.maximum_bytes_billed` を変更する |
| 出力を解釈できない、行数・イベント件数の和が合わない | 不完全な結果は保存されない。原因を除いて取り直す |
| 月が始まっていない・取得時期より前 | 見積もりは月の開始以降、取得は翌月2日（UTC）以降に行う |
| 分類できない `bq` の失敗 | 添えられた出力の先頭3行を確認する |

任意の属性の列が無い場合は、その属性が付いていないものとして集計し、名前を表示する。
`bq` の利用者設定（`.bigqueryrc`）は読ませない。SQL は標準入力、月と UUID は問い合わせの
引数で渡す。`--profile`・`--keep-browser`・`--timeout`・`--import`・`--setup`・
`--finish-setup`・`--login`・`--list-orgs`・`--check-login` は claude 専用で、otel に
付けると終了コード2。`--dry-run` は定義と見積もりだけで保存しない。

### otel-cache（collect が作るキャッシュ）

`input/<組織名>/otel-cache/otel-YYYY-MM.json` は1組織×1か月の集計。schema は1。
同じ月の再実行は原子的に置き換える。行の並びはイベントが email・date・name・区分の JSON
（キー昇順）、セッションが email・date・terminal の昇順になる。

| 項目 | 内容 |
|---|---|
| `schema`・`organization`・`month` | 形式の版、入力ディレクトリの組織名、対象月 |
| `source` | `project`・`dataset`・`table` の名前 |
| `organization_ids` | 絞り込みに使った小文字の組織 UUID |
| `scanned_events` | 月の範囲にあったイベントの総数 |
| `excluded_events` | `organization_empty`・`organization_other`・`email_empty` の件数。無い種類は0 |
| `absent_attributes` | 表に列が無かった任意属性の名前（昇順） |
| `query` | `estimated_bytes`（byte）と `executed_at`（実行日時 UTC） |
| `rows` | `email`・`date`・`name`・`attrs`・`count`。`api_request` だけトークン4項目も持つ |
| `sessions` | `email`・`date`・`terminal`・`count` |

`rows` の例（合成値）:

```json
{"email": "alice@example.com", "date": "2026-10-01", "name": "api_request",
 "attrs": {"terminal": "interactive", "model": "other", "origin": "main", "effort": "high",
           "agent": false, "skill": false, "mcp": false, "plugin": false},
 "count": 12, "input_tokens": 3400, "output_tokens": 5600,
 "cache_read_tokens": 120000, "cache_creation_tokens": 8000}
```

件数は正の整数、トークンは0以上の整数（元の NULL は0）。イベントが無い月も総数0の
空のキャッシュを作る。イベント件数の和と除外件数の和を足すと `scanned_events` になる。
セッション数はこの和に含めない。一意キーはイベントが email・date・集計名・区分の組、
セッションが email・date・端末の種類。

集計名と区分（`attrs` はその集計名の区分だけを持つ）:

| 集計名 | 区分 | 値と畳み方 |
|---|---|---|
| すべて | `terminal` | `terminal.type` が `non-interactive` なら `non_interactive`、それ以外と属性なしは `interactive` |
| `api_request` | `model` | 英数字と `.`・`_`・`:`・`[`・`]`・`-` だけの100字以内のモデル名。それ以外は `other` |
| `api_request` | `origin` | `query_source` が `repl_main_thread` なら `main`、`sdk` なら `sdk`、`agent:builtin:` で始まれば `subagent_builtin`、そのほかの `agent:` は `subagent_custom`、それ以外と属性なしは `other` |
| `api_request` | `effort` | `low`・`medium`・`high`・`xhigh`・`max`。属性なしは `none`、それ以外は `other` |
| `api_request` | `agent`・`skill`・`mcp`・`plugin` | エージェント・スキル・MCP サーバー・プラグインの名前の属性が付いているか（true / false） |
| `tool_decision` | `tool` | `edit`（Edit・Write・MultiEdit・NotebookEdit）・`shell`（Bash・PowerShell）・`mcp`・`agent`（Agent・Task）・`skill`（Skill）・`other` |
| `tool_decision` | `decision` | `accept`・`reject`・`other` |
| `tool_decision` | `source` | `config`・`hook`・`user_permanent`・`user_temporary`・`user_abort`・`user_reject`・`other` |
| `tool_decision` | `permission_mode` | `default`・`plan`・`acceptEdits`・`bypassPermissions`・`dontAsk`・`auto`。属性なしは `none`、それ以外は `other` |
| `user_prompt` | `command_source` | `builtin`・`custom`・`mcp`。属性なしは `none`、それ以外は `other` |
| そのほかのイベント | `terminal` だけ | 件数だけを持つ |
| セッション（イベントとは別） | `terminal` | 月内に `api_request` のあったセッションを、その月の最初の `api_request` の日に数える |

イベント名は `claude_code.` を除き、英小文字・数字・`_` の64字以内、それ以外は `other`。
`tool` の `mcp` は出どころ（`tool_source`）が `mcp` のもの。出どころの属性が無い場合は、
ツール名が `mcp_tool` または `mcp__` で始まるものを `mcp` にする。ホストの組み込みツール
（出どころが `sdk_host_builtin_mcp`）は、ツール名でほかの区分に分ける。
セッションは人ごとに数え、非対話の `api_request` が1件でもあれば `non_interactive`。
月をまたぐセッションは両方の月で1回ずつ数える。ID は保存しない。

保存しないものは、プロンプト・応答・API の本文、ツールの引数・入出力・コマンド、エラー文、
ホストのパス、リポジトリの URL・owner・名前、費用、セッション ID・request ID。
ツール・エージェント・スキル・プラグイン・MCP サーバー・コマンドの名前と `query_source`
の値自体も保存せず、上の区分か有無だけを持つ。本文・引数・パス・費用の列は SQL でも
参照しない。生の `bq` の応答と問い合わせの SQL も保存しない。

読み戻しでは schema・形・語彙・件数を検査し、`source` と `organization_ids` の集合が
現在の設定と違えば取り直しを案内する。UUID の並びだけの違いでは取り直さない。
取得しても、シートの判定と、組織の担当者へ共有する成果物は変わらない。
`adoption.enabled` を有効にした正式分析では、人 × 月の表・チーム × 月の表の OpenTelemetry の
列と、レポートの OpenTelemetry の指標に値が入る。

### 届いている割合の検査（doctor）

テレメトリが一部しか届いていない人の利用を過小に読み取らないよう、`doctor` は
`otel` を設定した組織で、人 × 月の届いている割合（網羅率）を確かめる。割合は、キャッシュの
`api_request` の出力トークンの合計を、スペンドレポート（spend）の対象 product の出力
トークンの合計で割った値。件数や費用は比較に使わない。

対象 product は `otel.coverage_products` で指定する。名前は前後の空白を除き、Unicode の
正規化形式と大文字小文字の違いを無視した完全一致で照合する。メールアドレスも前後の空白を
除いて小文字にそろえ、利用者の行を人ごとに突き合わせる。複数スペースの組織では、対象月に
始まっている全スペースの spend を合算する。

取得の対象の組織 UUID と spend を置いたスペースは、同じ範囲を指す前提。UUID が一部の
スペースだけを指すと、ほかのスペースの利用が届いていないと出る。spend を置いていない
スペースのイベントがキャッシュに入ると、比が高く出る。キャッシュは対象月の全体を観測して
いることが前提で、収集を月の途中から始めた月や、表の保持期間を過ぎてから取得した月は、
届いていた人も比が低く出る。

状態は次の表の上から順に当てはめる。

| 状態 | 条件 |
|---|---|
| `unknown`（判定できない） | キャッシュに出力トークンの属性が無いか、その人の spend に product 名が空の行、または対象 product で出力トークンを読めない行がある。product 列が無い明細の行も含む |
| `not_judged`（判定しない） | spend の対象 product の出力トークンの合計が 0、または設定した下限より小さい |
| `missing`（届いていない） | その人のイベントがキャッシュに1件も無い |
| `low`（低い） | 網羅率が設定した閾値を下回る |
| `ok` | 上のどの条件にも当てはまらない |

対象月のキャッシュが無い場合、開始済みのスペースに対象月の spend が無いか全月と
確かめられない場合、スペースの構成が設定と食い違う場合は検査しない。全月と確かめられるのは
ファイル名の期間が暦の日数に届くか、月だけの命名の場合。単日の日付の命名は、期間を
確かめられないため対象外。

| 警告 | 出るとき | 確かめること |
|---|---|---|
| `OTEL_COVERAGE_LOW` | `low` の人がいる | テレメトリの設定が入っていない端末で使っていないかを確かめる。多くの人の比と組織全体の比が低いときは、収集を月の途中に始めたか、取得した時点で表の保持期間を過ぎていなかったかも確かめる |
| `OTEL_USER_MISSING` | `missing` の人がいる | テレメトリの設定が端末に入っているか、利用者のメールアドレスの属性が届いているかを確かめる |
| `OTEL_COVERAGE_UNAVAILABLE` | キャッシュを読めないか出力トークン属性が無い、または `unknown` の人がいる | 理由に応じて、キャッシュの状態や設定、取得元の表の出力トークン属性、spend の product 名や対象 product の出力トークンを確かめる |

組織全体の比は、`unknown` を除き、spend に対象 product の出力トークンがある同じ人の集合で
分子と分母をそれぞれ合計して求める。比が 1 を超える側は検査しない。検査はローカルの
キャッシュと spend を使い、`doctor` は BigQuery に接続しない。

`adoption.enabled` を有効にした正式分析も `doctor` と同じ判定を使い、`low`・`missing`・
`unknown` の人の OpenTelemetry の件数の列を空欄にする。空欄にした人の全員は
adoption-people の `otel_coverage` で読める。`doctor` が名前を挙げるのは例だけ。

2つの表を書く実行では、OpenTelemetry を設定した組織について次の場合に通知する。

- 対象月の spend が全月と確かめられ、対象月のキャッシュが無いときは、取得のコマンドを案内する
- キャッシュを読めない月は、OpenTelemetry の値を空欄にして残りの分析を続け、月ごとに理由を
  伝える。理由の文に、キャッシュの取り直しかファイルの状態の確認の案内が入る
- 網羅率で人の件数の列を空欄にしたときは、該当する月と人数を1件にまとめる。
  `otel_coverage` の列で該当者を、`doctor` で理由と割合の例を確認できる

| 設定 | 意味と値の範囲 | 既定 |
|---|---|---|
| `otel.coverage_products` | OpenTelemetry のイベントとして届く product の一覧。空でない名前を1つ以上、照合規則で重複なく指定する。テレメトリの設定が届かない product は外す。全組織・全月に同じ一覧を適用する | `["Claude Code", "Cowork"]` |
| `otel.coverage_warning_ratio` | この比を下回る人を警告する。0 より大きく 1 以下の有限の数。真偽値は使えない | `0.7` |
| `otel.coverage_min_output_tokens` | 判定に使う spend の対象 product の出力トークンの下限。真偽値を除く 0 以上の整数。0 でも出力が 0 の人は判定しない | `100000` |

## モデル単価（config.yaml > model_prices）

API 換算需要は、モデル名の部分一致で引いた単価（USD per 1M tokens）で計算する。単価表は
`default-config.yaml` が持ち、プログラムの更新で新しい値が届く（上の「設定について」のとおり
ワークスペース側へは写さない）。どのパターンにも一致しないモデルは `default` の単価で試算し、
その旨が警告に載る。

各パターンは任意で `cache_read`（入力単価に対するキャッシュ読取の倍率）を持てる。持たない
パターンのモデルは `config.yaml > cache_multipliers` の `read` を倍率に使う。

## 判定ロジック概要

版は `--decision-version` の明示指定 > `config.yaml > decision.version` > 既定の v2 で決まる。
速報（`--preview`）は V2 判定を行わない。

### V2 の判定（既定）

需要は全 product の API 換算需要で、Claude Code か他の product かを条件にしない。
判定に使うのは観測（現シートの実課金・追加クレジット上限への到達）と方針線
`decision_v2.premium_justification_usd`（Premium に見合う需要の下限）だけ。
変更先シートの従量課金は推定せず、allowance は使わない。

- 降格（Premium → Standard）: 直近の完全月 `decision_v2.downgrade.min_complete_months` か月の
  すべてで、実課金が無く需要が方針線未満なら降格する
- 昇格（Standard → Premium）: 追加クレジット上限の状態で見る信号が変わる
  - 有効なら、実課金がシート差額を `decision_v2.observed_billing_margin_usd` 以上上回るか、
    上限に到達したときに昇格する
  - 無効（0）なら、対象月の需要が方針線以上で、それが続く（2完全月連続か月内の消費の継続上昇）
    と昇格し、1か月だけなら上限つき付与を提案する
  - 不明なら、実課金が条件を満たせば需要によらず昇格と設定確認、満たさず需要が方針線以上なら
    設定確認だけを出す（シートは動かさない）
  - 何も提案しないのは、無効で需要が方針線未満、有効で実課金も上限到達も条件に届かない、
    または不明で実課金も需要も条件に届かない Standard。
    有効・不明の人は需要が方針線未満でも実課金の条件で昇格しうる
- 保留と対象外: 対象月が部分月か判定に要る完全月が足りなければ「要観察（データ蓄積待ち）」、
  直近（`decision_v2.recent_seat_change_days`）の加入・シート変更、分類できないメンバー変動や
  照合の食い違いがあれば「要観察」。members に居なければ「シート不明」、
  シート未割当・固定シート・副スペースのアカウントは対象外になる
- 確度は方針線を ±$100 ずらしてもシートを変えるかの結論が同じか（高・中・低）を表す。
  削減見込みはシート差額ベースの比較額で、変更後の従量課金を含まず、負は費用増

各条件の細部は [実装設計書の §12](./roadmap/implementation-design.md#12-decision-v2)、
履歴の組み方は [decision-evidence の列](#decision-evidence-の列v2-判定)を参照。

### V1 の判定（`--decision-version v1`）

ユーザ×月ごとに API 換算コスト `api_cost` を集計し、シート込み利用量（allowance）の
モデルで各シートの月額を試算する。

```
cost_if_standard = $25  + max(0, api_cost − S_allowance)
cost_if_premium  = $125 + max(0, api_cost − P_allowance)
```

この試算を観測値と次のように組み合わせ、月額の安い方を推奨する（同額なら Standard）。

- 現シートの月額は試算ではなく観測値（シート料 + 対象月の実課金）を使う
- 変更先のシートの月額は上の式の試算を、込み量の大小関係（Standard ≤ Premium）を使って
  観測実課金で上下に抑える
  - Standard ユーザが Premium に変えた場合の超過分は、現在の実課金を超えない（試算と
    現在の実課金の小さい方）
  - Premium ユーザが Standard に変えた場合の超過分は、現在の実課金を下回らない（試算と
    現在の実課金の大きい方）
  - 帰結として、実課金がゼロの Standard ユーザは、需要がどれだけ大きくても Standard の月額が
    $25・Premium の月額が $125 になり、推奨は Standard のまま。Standard ユーザに Premium が
    推奨されるのは、実課金がシート差額（$100）を上回る月に限られる
- シートが不明（members に居ないのにスペンドに現れた）のユーザは観測値で抑えず、上の式の
  試算だけで推奨を出す（判定は「シート不明」）

このほか:

- allowance（シート込み利用量の USD 換算）は Anthropic 非公開のため、
  `config.yaml` の low / mid / high 3 シナリオで感度分析する（判定の主系は mid）
- ヒステリシス: 判定窓（対象月から暦で遡る 2 か月。`decision.hysteresis_months`）のどの月でも
  推奨が同じで、かつその月の削減見込みが差額 $100 の 20%（`decision.buffer_ratio`）以上のときだけ
  「変更推奨」にする。その月のスペンドに現れないユーザは需要 0 として判定する。推奨が現シートと
  違っても、次のどれかに当たれば「要観察（データ蓄積待ち）」にする（推奨シート・確度・削減見込みは
  そのまま出す）。V2 の履歴の扱いは
  [decision-evidence の列（V2 判定）](#decision-evidence-の列v2-判定)を参照
  - 判定窓にスペンドレポートの無い月がある。スペンドレポートのある最初の月より後の欠月は
    警告にも出す（それより前の月が無いのはデータが溜まっていないだけ）
  - 判定窓に部分月（ファイル名の期間が暦日数に満たない月）がある。期間の無い命名（単日日付・
    月のみ）は全月として扱う
  - 複数スペースの組織で、副スペースのスペンドレポートのある最初の月以降の判定窓の月に、副の
    スペンドレポートが無い、または部分月がある（主の全員が対象。副にアカウントがあるかは見分けない）
  - その人が判定窓のあいだに加入した、またはシート種別が変わった。判定窓の最初の月の 1 日以前で
    最新の members から、対象月の分析で採用した members までの各ファイル（代表日は期間の終わり。
    単日日付はその日、月のみはその月の末日）のどれかで、その人が居ない・シート種別が対象月と
    違えば当たる。加入・シート変更は、members のスナップショットで「居ない」「種別が違う」と
    確かめられたときだけ保留する。判定窓の始まり以前のファイルが無ければ、採用ファイル以前の
    全ファイルを見るので、窓の中のスナップショットの違いも見つけられる。見つけられないのは、
    最初に読める members より前の加入・シート変更
- 上限フラグ（⚠️・recommendations の `cap_suspected`）: 現シートが Standard で、対象月の
  実課金がゼロ、かつ需要が Standard の込み量推定（mid）の `decision.censoring_margin` 倍
  （既定 0.85）以上のユーザに付ける。「上限で止められて需要を過小評価している」のか
  「実効的な込み量が推定より大きい」のかはデータから区別できないので、本人への確認が要る。
  追加クレジットが有効なユーザには付けない（[追加クレジット（usage credits）の上限](#追加クレジットusage-creditsの上限)）
- シート未割当（Seat Tier: Unassigned）のメンバーは、意図的な未割当（別組織で
  アサイン済み・管理者等）として判定対象外にする。利用実績がある場合のみ警告

## allowance のキャリブレーション

数ヶ月分の実データが溜まったら:

- Standard ユーザの月次 `api_cost` の分布を確認し、上限到達（頭打ち）している
  ユーザの観測最大値 ≒ `S_allowance` として `config.yaml > seats` で上書き
- Premium は Standard の 5 倍程度（セッション倍率 1.25x vs 6.25x）を目安に設定

この較正が効くのは V1 の判定（変更先シートの月額の試算と、それを基準にする上限フラグ・
追加クレジット付与候補）と速報の一次判断だけ。既定の V2 の判定は allowance を使わず、
方針線 `decision_v2.premium_justification_usd` を使う
（[decision-evidence の列（V2 判定）](#decision-evidence-の列v2-判定)）。

## 判定の版と移行

既定の版は v2。従来の判定はワークスペースの `config.yaml` に `decision.version: v1` を書くか、
`--decision-version v1` で選べる。V1 は既定の切り替えから最低3か月残し、その後の版で削除する。

削除した設定キーがあると読み込み時にエラーになる。既存の設定は次のように直す。

- `decision_v2.enabled`: `true` は `decision.version: v2`、`false` は `decision.version: v1` に書き換える
- `decision_v2.upgrade.min_code_demand_usd`・`decision_v2.downgrade.max_code_demand_usd`: 消す

decision-evidence からは `code_demand_usd`・`supplementary_high` の2列を外した。
Claude Code の需要は usage-summary にある。v2 の recommendations は V1 だけの5列が無く
`reason` がある（[recommendations の列](#recommendations-の列)）。列名で参照する表計算などは直す。

既存の月を再生成すると、記入済みの「## 考察」は書き換わらずに引き継がれる。判定が変わった月は
`analyze --with-discussion --force-discussion` か `discuss --force` で書き直すか、手で直す。

速報は V2 判定を行わず、一次判断は込み利用量の推定に基づくため、月中の速報と正式分析の
結論が違うことがある。

## 設定キーと既定値

設定キーと既定値の一覧の正は、パッケージ同梱の既定設定ファイル
[`src/seat_analyzer/default-config.yaml`](../src/seat_analyzer/default-config.yaml) で、各キーの
意味はそこにコメントで書いてある（この文書には全キーの表を置かない）。

ワークスペースの `config.yaml` には、既定から変えたい差分だけを書く。辞書はキー単位で既定に
重なり、リストと単一の値は丸ごと置き換わる（一覧の一部だけを足すことはできない）。既定に
無いキー（`organizations` の直下の組織名と、その `workspaces` の直下の workspace 名を除く）・
型の違う値・空の値は、設定の読み込みでエラーになる。
