## 1. この文書の目的

実装設計書の仕様と、日々変わる進捗を分離して管理する。

- 実装内容・受け入れ条件: `implementation-design.md`
- 着手・完了・ブロック状況: 本文書
- 機能の背景・優先順位: `claude-adoption-cost-management-proposal.md`

実装設計を変更せずに、各Stepの進捗と検証結果を更新できるようにする。

## 2. ステータス

| ステータス | 意味 |
|---|---|
| `未着手` | 作業を開始していない |
| `進行中` | 現在作業中 |
| `ブロック` | 外部条件・判断待ちで進められない |
| `完了` | 受け入れ条件と必要な検証を満たした |
| `見送り` | 検証結果または方針により実装しない |

`条件付き完了`は使用しない。制約を発見すること自体が目的のFeasibility Stepは、
制約と対応方針を検証記録へ残したうえで`完了`とする。

## 3. 更新ルール

### 着手時

1. 対象Stepを`進行中`へ変更する
2. 同時に複数Stepを`進行中`にしない
3. 依存Stepが`完了`していることを確認する

ステータスを変えたら「進捗サマリ」の件数も同じ変更で更新する（Step一覧とサマリが
食い違うと、どちらが現状か分からなくなる）。

### 完了時

1. 設計書の受け入れ条件をすべて確認する
2. 必要なテスト・smoke testを実行する
3. 本文書を`完了`へ更新する
4. 完了日と検証結果を「検証記録」へ追記する
5. 次のタスクを更新する

### ブロック時

1. ステータスを`ブロック`へ変更する
2. ブロック理由を検証記録へ記載する
3. 解消条件を明記する
4. 独立して進められる次Stepがなければ作業を止める

### 公開情報

本文書には次を記載しない。

- 実在するOrganization名
- 実在するrepository名
- メンバー名・メール
- 実利用金額
- 組織ごとの実人数・実件数
- token、Cookie、認証情報

検証結果は、実装判断に必要な内容へ一般化して記載する。

### 2026-08-29 — Step 32: GitHub mapping loader

- `github_collect.py`（層15）を新設。`input/<組織名>/github-members.csv`（email → GitHub
  loginの対応表。設計書§7.3）を読む正準loaderで、公開APIは`load_github_members(input_dir,
  cfg)`と`unmapped_emails(members, emails)`の2つ。ファイルを書かず、`gh`もネットワークも
  呼ばず、現在時刻も参照しない。どこからも呼ばれていない（結線はStep 33以降）
- GitHub分析は組織ごとのopt-inとする前提を設計書§15.1へ追記した。`organizations.<組織名>.
  github_org`を設定した組織だけが収集・doctor検査・指標・出力の対象で、未設定の組織は
  GitHub関連の処理と警告から一切除外される。ゲートを持つのは消費側で、loaderは持たない
  （純粋な読み取りに徹し、判断を呼び出し側へ残す）
- 「未提供」と「ファイルはあるがデータ行が無い」を`source`（由来ファイルのbasename。無ければ
  None）で区別する。ファイルが無いことはエラーにしない（設計書§20.2「GitHubなしでも分析
  できる」）。ヘッダだけのファイルは警告を1件出して空の結果にする
- 受け入れ条件「duplicate error」: emailの重複（正規化後の比較）とgithub_loginの重複で
  ValueError。loginの重複は大文字小文字を区別せずに見る（GitHubのloginは大小を区別せず、
  `Foo`と`foo`は同じ1人を指すため）。emailの欠落と必須カラムの欠落も同じく中止する
- 受け入れ条件「missing warning」: loginの空欄と、GitHubのloginとして読めない字句は
  None（＝未対応）にして警告に残す。警告の発行は`unmapped_emails`の呼び出し側（Step 33・36）
  の責務にし、loaderは照合結果だけを返す
- loginの字句は英数字・ハイフン・アンダースコアの1〜39文字で、先頭と末尾は英数字、ハイフンは
  連続せず、アンダースコアは高々1個（Enterprise Managed Usersのloginが
  `<ユーザー名>_<shortcode>`の形をとるため区切りの1個は受ける。shortcodeの形そのものは
  検証しない）。実在しない形を通すと、対応づいたつもりのloginが後段の突き合わせで静かに何にも
  一致しないため、未対応として警告に出す。先頭の`@`のような余分な文字も黙って取り除かず警告に
  する（取り除くと別人のloginを正しい値として通す余地が残る）
- ヘッダの正準化は`ingest.map_columns`に任せ、エイリアスの重複検査とヘッダの曖昧さ検査は
  `admin_inputs`と同じ規則をモジュール内に持たせた（同層どうしはimportできないため実装は
  共有していない。共有する場合は層10へ下ろす別の変更になる）
- 0バイトのファイルは読み込みライブラリの例外ではなく、ファイル名を挙げたValueErrorにする
  （先頭行の読み取りで`EmptyDataError`を受けてヘッダ無しとして扱う）
- 全データ行がヘッダより1列多い表も中止する。読み込みが先頭の列を暗黙の行ラベルにして残りが
  1つずつずれ、ずれた値はemailとしてもloginとしても字句上は通るため、止めなければ誤った対応が
  警告なしで採用される。正常な読み取りならデータ行が無くても付く`RangeIndex`でなければ中止と
  した（一部の行だけ列数が多い場合は読み込み側のParserErrorで止まるので触っていない）
- 警告にはファイル名だけを載せ、絶対パスを持たせない（値を実行環境に依存させない）。警告の
  並びは行順で、同じ入力からは常に同じ結果と同じ並びになることをテストで固定した
- `columns.github_members`を`default-config.yaml`へ追加し、`ingest.REQUIRED_COLUMNS`へ
  `github_members`（email・github_login）を追加した。config検証はこの1箇所を参照するので、
  セクションの欠落は既存の検査で落ちる
- 外部レビュー（codex 1巡目）: mid 2件。①pandasの既定のNA変換で`NA`等のloginが欠損になる件は
  不採用（人手の表で`NA`は「アカウントなし」の意図が大半で、現挙動＝未対応+警告がその意図
  どおり。`na_filter`を切ると`NA`が有効なloginとして黙って採用され、静かな誤対応になり悪化
  する）②login字句規則の厳格化は縮小して採用（連続ハイフン・アンダースコア2個以上・先頭末尾の
  アンダースコアを拒否するのみ。EMUのshortcode形式の検証はモデル化しすぎで不採用）
- 外部レビュー（codex 2巡目）: mid 1件・low 1件。①ヘッダより全データ行が1列多いCSVで読み込みが
