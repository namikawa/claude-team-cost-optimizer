## 1. この文書の目的

実装設計書の仕様と、日々変わる進捗を分離して管理する。

- 実装内容・受け入れ条件: `implementation-design.md`
- 着手・完了・ブロック状況: 本文書
- 機能の背景・優先順位: `claude-adoption-cost-management-proposal.md`

実装設計を変更せずに、各Stepの進捗と検証結果を更新できるようにする。

## 2. ステータス

| ステータス | 意味 |
|---|---|
| `未着手` | 作業を開始していない |
| `進行中` | 現在作業中 |
| `ブロック` | 外部条件・判断待ちで進められない |
| `完了` | 受け入れ条件と必要な検証を満たした |
| `見送り` | 検証結果または方針により実装しない |

`条件付き完了`は使用しない。制約を発見すること自体が目的のFeasibility Stepは、
制約と対応方針を検証記録へ残したうえで`完了`とする。

## 3. 更新ルール

### 着手時

1. 対象Stepを`進行中`へ変更する
2. 同時に複数Stepを`進行中`にしない
3. 依存Stepが`完了`していることを確認する

### 完了時

1. 設計書の受け入れ条件をすべて確認する
2. 必要なテスト・smoke testを実行する
3. 本文書を`完了`へ更新する
4. 完了日と検証結果を「検証記録」へ追記する
5. 次のタスクを更新する

### ブロック時

1. ステータスを`ブロック`へ変更する
2. ブロック理由を検証記録へ記載する
3. 解消条件を明記する
4. 独立して進められる次Stepがなければ作業を止める

### 公開情報

本文書には次を記載しない。

- 実在するOrganization名
- 実在するrepository名
- メンバー名・メール
- 実利用金額
- 組織ごとの実人数・実件数
- token、Cookie、認証情報

検証結果は、実装判断に必要な内容へ一般化して記載する。

### 2026-08-20 — 成果物のファイル名に月と組織名を含める

Stepではなく、共有時の運用で出た要望による命名の変更。

変えた理由:

- 成果物は共有のためフォルダの外へ出る。種別だけの名前（`report.md`等）では、
  どの組織のいつの分析かがファイル名から分からない

変えたこと:

- 組織×月ディレクトリに出る7種を`{種別}-{YYYYMM}-{組織名}.{拡張子}`にした
  （正式5: report・details・dashboard・recommendations・usage-summary /
  速報2: preview・preview-dashboard）。月はハイフン無しで、ディレクトリ名（`YYYY-MM`）は
  変えない。種別名は従来のベース名のまま
- 組織横断サマリ`reports/summary/<月>.md`は対象外。担当者へ共有しない内部の文書で、
  月は既に名前に入っているため
- 名前の組み立ては`report/naming.py`（層30）の`Artifact`1箇所に置き、`report`と
  `discussion`の両方がそこを通す。`discussion`は`org`を明示的に引数で受け取る
  （`org_output.name`から逆算しない）

旧名の扱い:

- 自動の改名・削除はしない。`reports/`には意図的に残された旧デザインの成果物や
  手置きの比較用ファイルがあり、ツールが動かすと壊れる。再生成すると新旧が併存する
- 読み取りだけ「新名優先 → 旧名フォールバック」で解決する（`Artifact.existing_path`）。
  対象は考察の引き継ぎ（`_preserve_discussion`）と`discuss`の資料（本文・details・
  recommendations・前月の考察）。手書きの考察は他のどこにも無いので、改名後の最初の
  再生成で読み落とすと失われる
- `discuss`は読んだ文書をその場で書き換えるため、旧名だけの月では書き先も旧名になる
  （読み先と書き先を揃える）

確認したこと:

- 中身の差分は「ファイル名に言及している箇所」だけ。goldenの再生成で変わったのは
  詳細資料の冒頭がダッシュボードのファイル名を指す1行と、横断サマリの各組織へのリンクと
  末尾の案内。他の生成物はすべて旧版とバイト一致
- 旧名だけの月で考察が引き継がれること、`discuss`が旧名の資料を読めること、
  新旧が併存する場合は新名が優先されること、旧名のファイルが再生成で消えないことを
  `tests/test_output_filenames.py`で固定した
- `leakcheck`が他組織の禁止語を集める経路は拡張子（`.csv`/`.md`）で走査しており、
  ファイル名に依存していない（改名の影響を受けない）

外部レビュー Round 1: 指摘4件（mid 2・low 2）。採用3・一部採用1。goldenは全ケース不変。

  「置換直前に内容が変わっていて書けなかった」の2つの意味で返しており、`generate`が
  両方を`kept`にしていたため、後者でも「記入済みの考察があるため変更しません

### 2026-08-20 — 入出力ディレクトリをconfig.yamlのpathsで指定できるようにする

Stepではなく、CSVとレポートをワークスペースの外に置く運用のための設定の追加。

変えたこと:

- `paths.input` / `paths.output`を`default-config.yaml`に新設した。優先順位は
  CLIフラグ > ワークスペースの`config.yaml` > 組み込み既定。フラグのargparse defaultを
  `None`にして「明示されたか」を区別する
- configに書いた相対パスは、そのconfigファイルの置き場所を基準に絶対化する。`--config`で
  別のCWDから読んでも同じ場所を指すため、ワークスペースが自己完結する。`~`は展開する

### 2026-08-16 — members の採用ファイルを対象月末に最も近いスナップショットにする（不具合修正）

Stepではなく、実データの再生成中に見つかった不具合の修正。

見つかった不具合:

- `load_members` は「月単位で1つに畳む→月を選ぶ」の2段階で、畳む側（`_resolve_duplicates`）が
  同一月の単日スナップショットから最新日付を採っていた。未来月フォールバック（対象月の
  members が無く未来のファイルしか無い場合）では、月の選び方は最も近い未来の月で正しいのに、
  その月の中では最も遠い日付が選ばれる
- 帰結として、未来のスナップショットが増えるたびに過去月の判定が静かに変わる。実際に、
  対象月当時のmembersが無い組織で、翌月中旬のシート変更・メンバー追加が対象月の判定に
  持ち込まれていた（対象月の実態と違う人数・シート種別でレポートが生成されていた）

直した規則（ユーザ承認済み）:

- 月ではなくファイル単位で「対象月の末日に最も近いもの」を採る。代表日は期間の終わり
  （単日スナップショットはその日、月のみの命名はその月の末日）。同距離のタイブレークは
  末日以前→期間の広い方→ファイル名の昇順
- 根拠は運用の実態。月末までのデータは翌月の最初の営業日に取得することが多く、対象月末
  時点の構成は翌月初のファイルに入っている。「月末に最も近いもの」はこの運用と、対象月内で
  最新を採る従来の意図（月末時点の構成が欲しい）を1つの規則で表す

- 日数の条件は `is_near_month_end()` に閉じ、`load_members` の強い注意と `doctor` の
  MISSING_MEMBERS 警告が同じ述語を見る。doctor も通常運用の範囲では警告しない
- 重複解決は採用したファイルの月にだけ掛ける。採用した月が曖昧なら従来どおり `ValueError`

このStepで得た教訓:

- 新しい経路を追加したら、既存経路に対して確立した不変条件（messageの決定性・JSON出力の
  保証・error/warningの分類）を同じ強さで満たしているかを必ず確認する。指摘の3分の1は
  「前巡の修正が作った新しい経路」由来だった
- 例外メッセージを再利用して構造化issueへ載せる場合、環境依存値の除去は素朴な部分文字列
  置換では成立しない。置換対象を絶対パスに限る等、対象を狭く定義する
- 「doctorが検査する」と決めた不整合は、対象月あり・なしの両経路で同じ強さで検査する。
  片方だけ緩いと、その経路でのみ無言の欠落が起きる
