# 出力形式（厳守）

- 出力は考察セクションの本文だけ。挨拶・前置き・後書き・作業報告・自己言及を書かない
- 「## 考察」という見出し自体は出力しない。小見出しは `###` を使う
- 小見出しは観点の名前をそのまま置かず、その月の結論が分かる具体的な文にする
  （例: 「### 変更推奨の妥当性」ではなく「### 変更推奨2名のうち1名は新規加入のため確定を保留」）
- 太字（`**`）を見出しの代用にしない。強調は本当に要点となる箇所に限る
- 全体をコードフェンス（```）で囲まない
- 資料に無い数値・固有名詞を推定や創作で書かない。数値はすべて資料から引用する
- 事実（数値）と解釈を分けて書く。断定できないことは「可能性」「要確認」として書く

# 執筆の原則（厳守）

この考察は対象組織「{{ORG}}」の担当者に共有される。

- 資料に現れない組織名・ディレクトリ名・ユーザ名・メールアドレス・金額・行数・
  リクエスト数・部署名を、いかなる箇所にも書かない
- 他組織との比較や他組織の事例を書かない。一般的な知見を根拠に使う場合は、
  出典組織を特定できない一般論として書く（例:「一般に〜という現象が起きる」）
- 対象組織の担当者が読んで、他組織の存在や規模を推測できる記述を残さない

# 検証すべき点（考察を書く前に資料の上で確認する）

- 極端な API 換算需要や前月からの急変が、データの不備ではなく実態として説明できるか
- シート不明（unknown）のユーザがいる場合、メンバー一覧の更新漏れの可能性に触れる。
  「対象外（シート未割当）」は意図的な未割当なので指摘しない
- 部分月データ・メンバー一覧のフォールバック・スナップショット不足など、判定の信頼度を
  下げる条件が資料の警告に出ていないか。出ている場合は結論にその限界を明記する
- コード行数（LoC）の欠落を「Claude Code を使っていない」「コードを書いていない」の根拠に
  しない。LoC と製品別内訳は網羅範囲が両方向に一致しない。逆向き（LoC があれば実際に
  コードを書いた）は成立するので、活用度の裏付けには使ってよい
